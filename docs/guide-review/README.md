## 1. 何を目指す Wiki に変えたか

最初の目標は、インストールした人が小さなワールドを 1 つ作り、保存して Play で確認できることです。

主な導線は「インストール → ビジュアルエディターを開く → 球を置く → マテリアルを作って割り当てる → 色を変える → 保存 → Play」です。公開、外部素材、AI、コード制作は、その体験を終えた後で必要に応じて読める位置に置きました。最初のページで Node.js・CLI・MCP・ビルドを理解する必要はありません。

公開上の名称は「使い方ガイド」としつつ、既存の共有リンクを壊さないよう配信先の `/wiki/` は維持しています。「今したい操作」から探せる入口を目指しました。

対象読者は 3 つに分けています。初めての人は一本道のチュートリアル、制作中の人は目的別の記事と文脈ヘルプ、困った人は症状別の確認から入れる構成です。ソースをビルド・改造する人やコードで制作する人向けの詳細は GitHub 側の資料に分離しました。高度な制作機能そのものを削除したわけではありません。

## 4. 初回利用と制作中の体験

### 初回利用

紹介サイトの「使い方」またはダウンロード後の案内 → ガイドトップ →「インストールから始める」→ アプリの起動 →「セットアップせずに作り始める」→「ワールドを作る」という順序で進めます。すでに導入済みの人向けには、トップから「制作を始める」へ進む短い入口も別に用意しました。

アプリの最初の画面では、もともと存在していたワールド・アイテムの編集開始ボタンを先頭に移動しています。作成処理には既存のコールバックを使い、新しい API は追加していません。公開用ツールの準備は「公開の準備（後からでもできます）」に分けました。

最初のワールドでは、外部サイトで素材を探したり AI を設定したりせず、標準の球を配置して色を変えます。配置、質感、保存、動作確認を 1 つの短い例でつなぎました。自動保存や公開状態の仕様を無理に単純化せず、保存と再開の説明を別に用意しています。

### 制作中の文脈ヘルプ

| 場所 | 開く説明・動作 |
| --- | --- |
| 初回画面 | 最初のワールドの作り方 |
| プロジェクト一覧 | 使い方ガイド |
| エディターの左下 | いつでも「使い方」。画面操作・色と質感・保存にも進める |
| Assets | モデルや画像を取り込む説明 |
| マテリアル編集 | マテリアルの作成、割り当て、色と質感 |
| シーン設定 | ライト、空と水 |
| 公開ダイアログ | 公開手順をブラウザで開く（フォームは閉じない） |
| 問い合わせ画面 | AI への質問やログ送付の前に、症状から調べる入口 |

アプリ内ヘルプは画面左側の非モーダルパネルです。右側の Inspector や上部の操作を全面的に覆わないため、説明を読みながら編集できます。ただし、エディターのレイアウト幅を自動で組み替えるドッキング機能ではなく、狭いウィンドウでの実機上の重なり具合は公開前に確認する必要があります。

ヘルプは 1 つの Host で管理し、ページ選択、本文内目次、戻る、関連記事、閉じる、ブラウザで大きく読む機能を用意しました。閉じると元のボタンにフォーカスを戻します。ヘルプ内で Delete などを押しても編集側のショートカットには伝わりません。ヘルプを開く処理に、プロジェクトの変更・保存・送信は含めていません。

既存の公開・問い合わせモーダルの中からは外部ブラウザで開きます。別のモーダルを重ねて、送信中の状態や入力中の内容を見失わせないためです。外部ブラウザを開く処理には既存の Tauri ラッパーを使います。

## 5. マテリアルの説明をどう変えたか

基本ページを、機能名と数値の羅列から「次に何をするか」に沿った操作説明に書き換えました。

まず、マテリアルは物の色や光の反射を決める設定であると説明します。続いて Assets で作成し、対象を選び、Inspector の「メッシュの描画」から割り当てます。作っただけでは見た目が変わらないことも操作の流れに含めました。そのうえで Base Color、Metallic、Roughness を試します。

数値例はあくまで出発点として示し、どの光やモデルでも同じ見た目になるとは書いていません。複数のオブジェクトが同じマテリアルを共有する場合の注意点や、色が変わらないときの確認手順も基本ページに置きました。

テクスチャ、半透明・切り抜き・ガラス、Clearcoat・Iridescence などは別ページに分け、最初の色変更の途中で薄膜や屈折の詳細まで理解させる構成にはしていません。

Entity / Hierarchy / Inspector / Assets / Components や Roughness / Clearcoat / Iridescence は画面と同じ英語表記を維持し、独自の日本語名に置き換えずに効果を自然な日本語で説明しています。Normal Map と形状変形、Alpha と Transmission、Emissive と Bloom、Skybox と IBL は混同しないよう区別して説明しました。

## 7. 表示基盤をどう選んだか

採用したのは、公開版は静的 HTML、アプリ内は同じ Markdown を必要時に表示する構成です。公開ガイドをエディター本体の SPA として動かす方式をやめました。

公開版では、既存の依存パッケージである `react-markdown`、`remark-gfm`、`react-dom/server` をビルド時だけ使います。ブラウザには完成した本文 HTML を配信し、検索と旧 URL 移行だけを小さな JavaScript で補います。本文を読むためだけにアプリの React 起動処理、3D 表示、Monaco、`src/index.css` を読み込む必要はありません。

アプリ内版は同じ原稿を遅延読み込みします。記事の内容・タイトル・関連ページ・リンク規則が二重管理にならない構成です。アプリ内はページ選択と目次、公開版は本文検索という役割分担にしました。ネイティブアプリに本文を同梱して読む設計ですが、実機でのオフライン検証は未実施であり、公開サイト側のオフラインキャッシュを実装したわけではありません。

### ほかの方法との比較

| 選択肢 | 今回の評価 |
| --- | --- |
| 既存 Wiki の CSS だけを変更 | 初回導線・本文・ハッシュ衝突・二重管理を解決できないため不採用 |
| GitHub 上の Wiki や Markdown を利用者の主画面にする | 開発資料の移管先としては使うが、アプリ内の文脈ヘルプや初回体験の主画面にはしない |
| VitePress など専用の静的サイト生成器 | 有力な選択肢。VitePress は Markdown から静的 HTML を生成し、標準テーマにローカル検索を備える。ただし今回は既存 React アプリとの本文共有を優先し、新しい表示フレームワークと依存関係の追加を見送った |
| 既存 Markdown レンダラー + 静的 HTML + 共通原稿 | 今回採用。ブラウザ標準の URL・アンカー・`details`・`dialog` を使い、独自 SPA ルーターを増やさない |

HTML テンプレート、索引、表示 CSS は引き続き独自に保守する必要があります。「どんな規模でもこの方式が最良」と主張するものではありません。多言語対応、多数バージョンの管理、複雑な検索が必要になった段階では、専用生成器への移行を再検討できます。本文を通常の Markdown にしているのは、将来の移行を妨げないためでもあります。

VitePress の機能について参照した一次資料は `https://vitepress.dev/guide/what-is-vitepress` と `https://vitepress.dev/reference/default-theme-search` です。今回これらのパッケージを導入して動作比較したわけではありません。

## 8. スマートフォンと検索

狭い画面では単列レイアウト、本文 16px 以上、長い見出しも折り返す構成にしました。上部に「目次から探す」と「困ったとき」を置き、初回導入の主ボタンは幅 320px の最初の表示領域でも届く位置に配置しています。モバイル表示で本文を細いサイドバーに挟みません。

320 CSS px 幅でのリフローを確認する方針は W3C の SC 1.4.10 の解説を参照しました。検索ダイアログの Escape キー、閉じるボタン、起点へのフォーカス復帰は WAI-ARIA の Dialog パターンを参照しています。ただし、スクリーンリーダーやコントラスト比を含む WCAG 全体の適合検査は実施しておらず、適合を保証するものではありません。

参照: `https://www.w3.org/WAI/WCAG22/Understanding/reflow` / `https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/`

検索索引は 30 ページ・201 セクションです。本文、見出し、日本語の別名、英語の項目名を対象に検索します。「ラフネス」「色 変わらない」のような入力にも対応し、結果は該当見出し付きのリンクとして返します。検索語を外部サービスに送信することはありません。

検索中・該当なし・読み込み失敗・再試行の状態を分けて表示し、検索に失敗しても本文と目次は利用できます。結果が多くても閉じるボタンが画面外に押し出されないよう、検索結果の領域だけをスクロールさせます。

検索方式は文字列の正規化と部分一致、空白区切りの AND 検索です。日本語の形態素解析や高度な誤字補正は実装していないため、検索語は手動の別名で補う必要があります。

## 12. 納品物と変更の適用

`xrift-studio-wiki-rebuilt.zip` は、添付版をベースにした更新後のプロジェクト一式です。依存パッケージ、生成物キャッシュ、Git の管理領域は含めていません。`xrift-studio-wiki-rebuild.patch` は添付された元のソースとの差分で、追加・削除・画像を含みます。

この差分は添付された版に対するものです。その後に別の変更が入った作業ディレクトリに ZIP で上書きしないでください。作業ブランチで差分を確認し、未コミットの変更を退避・保護してから適用してください。元の添付版と同じソースであれば、最初に `git apply --check` で適用できるかを確認できます。

今回の再設計では、説明を読んで操作し、困った場所から必要な説明へ戻れる構成を目指しました。公開前の通し検証と実機スクリーンショットの差し替えが残っている点を、実装済みの範囲と区別して扱ってください。
