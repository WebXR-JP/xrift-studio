成果物は、既存Wikiの構成を手直しした提案書ではなく、公開ガイドの原稿・表示基盤・アプリ内ヘルプ・入口を置き換えたソースです。公開サイトへのデプロイ、GitHubへのコミットやプッシュ、インストーラーの配布は行っていません。

**重要な確認範囲：** 原稿、ローカルリンク、表示テンプレート、検索などは検査しました。一方、依存パッケージを取得できない環境だったため、通常のViteビルド、プロジェクト全体の型検査、Tauri実機での操作は未検証です。掲載したスクリーンショットは表示テンプレートの検証画像であり、変更後のアプリ実機画像ではありません。詳細は「検証結果」に記載します。

## 1. 何を目指すWikiに変えたか

最初の成功を「機能をたくさん知ること」ではなく、**インストールした人が、小さなワールドを一つ作り、保存してPlayで確認できること**に置きました。

主導線は、インストール → ビジュアルエディターを開く → 球を置く → マテリアルを作って割り当てる → 色を変える → 保存 → Playです。公開、外部素材、AI、コード制作は、その成功の後で必要に応じて読める位置にします。最初のページでNode.js、CLI、MCP、ビルドを理解する必要はありません。

公開上の呼び方は「使い方ガイド」としました。既存の共有先を壊さないよう、配信先の `/wiki/` は維持します。「Wikiという仕組み」を学ばせるのではなく、「今したい操作」を見つける入口にします。

対象読者は三つに分けています。初めての人は一本道のチュートリアル、制作中の人は目的別の記事と文脈ヘルプ、困った人は症状別の確認から入ります。ソースをビルド・改造する人、コードで制作する人向けの詳細はGitHub側の資料へ分離しました。高度な制作機能そのものを削除してはいません。

## 4. 初回利用と、制作中の体験

### 初回利用

紹介サイトの「使い方」またはダウンロード後の案内 → ガイドトップ → 「インストールから始める」 → アプリの起動 → 「セットアップせずに作り始める」→「ワールドを作る」という順序です。すでに導入済みの人には、トップから「制作を始める」へ進む短い入口を別に用意しました。

アプリの最初の画面では、もともと存在したワールド／アイテムの編集開始を先頭に移動しています。新しい未検証の作成APIを追加したのではなく、既存のコールバックを使っています。公開用ツールの準備は「公開の準備（後からでもできます）」に分けました。

最初のワールドは、外部サイトで素材を探したりAIを設定したりせず、標準の球を配置して色を変えます。配置、質感、保存、動作確認を一つの短い例でつなぎます。自動保存や公開状態の仕様を勝手に単純化せず、保存と再開の説明を別に用意しました。

### 制作中の文脈ヘルプ

| 場所 | 開く説明・動作 |
| --- | --- |
| 初回画面 | 最初のワールドの作り方 |
| プロジェクト一覧 | 使い方ガイド |
| エディターの左下 | いつでも「使い方」。画面操作・色と質感・保存へも進める |
| Assets | モデルや画像を取り込む説明 |
| マテリアル編集 | マテリアルの作成、割り当て、色と質感 |
| シーン設定 | ライト、空と水 |
| 公開ダイアログ | 公開手順をブラウザーで開く。フォームを閉じない |
| 問い合わせ画面 | AIへの質問やログ送付の前に、症状から調べる入口 |

アプリ内ヘルプは画面左側の非モーダルパネルです。右側のInspectorや上部の操作を全面的に覆わず、説明を読みながら編集できます。ただし、エディターのレイアウト幅を自動で組み替えるドッキング機能ではありません。狭いウィンドウでの実機上の重なり具合は、公開前に確認する必要があります。

ヘルプは一つのHostで管理し、ページ選択、本文内目次、戻る、関連記事、閉じる、ブラウザーで大きく読むを用意しました。閉じると元のボタンへフォーカスを戻します。ヘルプ内でDeleteなどを押したときに編集側のショートカットへ伝わらないようにしています。ヘルプを開く処理に、プロジェクトの変更・保存・送信は含めていません。

既存の公開／問い合わせモーダルの中からはブラウザーへ開きます。別のモーダルを重ねて、送信中の状態や入力中の内容を見失わせないためです。外部ブラウザーを開く処理は既存のTauriラッパーを使います。

## 5. マテリアルの説明をどう変えたか

基本ページを、機能名と数値の羅列から次の操作の説明へ置き換えました。

まず、マテリアルは物の色や光の反射を決める設定だと説明します。続いてAssetsで作り、対象を選び、Inspectorの「メッシュの描画」から割り当てます。作っただけでは見た目が変わらないことを、操作の流れに含めました。その後にBase Color、Metallic、Roughnessを試します。

数値例は出発点として示し、どの光やモデルでも必ず同じ見た目になるとは書いていません。複数の物が同じマテリアルを共有する場合の注意、色が変わらないときの確認も基本ページに置きました。

テクスチャ、半透明・切り抜き・ガラス、Clearcoat・Iridescenceなどは別ページです。最初の色変更の途中で、薄膜や屈折の詳細を理解させる構成にはしていません。

Entity / Hierarchy / Inspector / Assets / Componentsや、Roughness / Clearcoat / Iridescenceは画面と同じ英語表記を維持しています。独自の日本語名へ置き換えず、効果を自然な日本語で説明します。Normal Mapと形状変形、AlphaとTransmission、EmissiveとBloom、SkyboxとIBLは区別して説明しています。

## 7. 表示基盤をどう選んだか

採用したのは、**公開は静的HTML、アプリ内は同じMarkdownを必要時に表示する構成**です。公開ガイドをエディター本体のSPAとして動かす方式をやめました。

公開版は、既存依存の `react-markdown`、`remark-gfm`、`react-dom/server` をビルド時だけ使います。ブラウザーには完成した本文を届け、検索と旧URL移行などだけ小さなJavaScriptで補います。本文を読むためにアプリのReact起動処理、3D表示、Monaco、`src/index.css` を読み込む必要はありません。

アプリ内版は同じ原稿を遅延ロードします。記事の内容、タイトル、関連ページ、リンク規則が別管理にならないようにしました。アプリ内はページ選択と目次、公開版は本文検索という役割分担です。ネイティブアプリに本文を同梱して読む設計ですが、実機オフライン検証は未実施であり、公開サイトのオフラインキャッシュを実装したわけではありません。

### 他の方法との比較

| 選択肢 | 今回の評価 |
| --- | --- |
| 既存WikiのCSSだけを変更 | 初回導線・本文・hash衝突・二重管理を解決しないため不採用 |
| GitHub上のWiki／Markdownを利用者の主画面にする | 開発資料の移管先としては使うが、アプリ内の文脈ヘルプと初回体験の主画面にはしない |
| VitePressなど専用の静的サイト生成器 | 有力な選択肢。VitePressはMarkdownから静的HTMLを生成し、標準テーマにローカル検索を備える。ただし今回は既存Reactアプリとの本文共有を優先し、新しい表示フレームワークと依存関係の追加を見送った |
| 既存Markdownレンダラー＋静的HTML＋共通原稿 | 今回採用。ブラウザー標準のURL・アンカー・details・dialogを使い、独自SPAルーターを増やさない |

独自部分がゼロになったわけではありません。HTMLテンプレート、索引、表示CSSの保守は必要です。「どんな規模でもこの方式が最良」とは主張していません。多言語、多数のバージョン、複雑な検索が必要になった段階では専用生成器への移行を再検討できます。本文を通常のMarkdownにしているのは、その移行を妨げないためでもあります。

VitePressの機能について参照した一次資料は `https://vitepress.dev/guide/what-is-vitepress` と `https://vitepress.dev/reference/default-theme-search` です。今回これらのパッケージを導入・動作比較したわけではありません。

## 8. スマートフォンと検索

狭い画面は単列、本文16px以上、見出しが長くても折り返す構成です。上部に「目次から探す」と「困ったとき」を置き、初回導入の主ボタンは幅320pxの最初の表示領域でも到達できる位置にしました。モバイルで本文を細いサイドバーに挟みません。

320 CSS px幅でのリフローを確認する方針はW3CのSC 1.4.10の解説を参照しています。検索ダイアログのEscape、閉じるボタン、起点へのフォーカス復帰はWAI-ARIAのDialogパターンを参照しました。ただし、スクリーンリーダーやコントラストを含むWCAG全体の適合検査は実施しておらず、適合を認証するものではありません。

参照：`https://www.w3.org/WAI/WCAG22/Understanding/reflow` ／ `https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/`

検索索引は30ページ・201セクションです。本文、見出し、日本語の別名、英語の項目名を検索します。「ラフネス」「色 変わらない」のような入力を扱い、結果は該当見出し付きのリンクを返します。検索語は外部サービスへ送信しません。

検索中、該当なし、読み込み失敗、再試行を分けています。検索に失敗しても本文と目次は使えます。結果を大量に出して画面外へ閉じるボタンが消えないよう、検索結果だけをスクロールさせます。

検索方式は正規化と部分一致、空白区切りのAND検索です。日本語の形態素解析や高度な誤字補正を実装したわけではありません。検索語を手動の別名で補う必要があります。

## 12. 納品物と変更の適用

`xrift-studio-wiki-rebuilt.zip` は、添付版をベースにした更新後のプロジェクト一式です。依存パッケージ、生成物キャッシュ、Gitの管理領域は含めません。`xrift-studio-wiki-rebuild.patch` は添付された元のソースとの差分で、追加・削除・画像を含みます。

この差分は添付された版に対するものです。その後に別の変更が入った作業ディレクトリーへ、ZIPで上書きしないでください。作業ブランチで差分を確認し、未コミットの変更を保護してから適用してください。元の添付版と同じソースなら、最初に `git apply --check` で適用可能性を確認できます。

このレビューの再設計は、ページ数を増やすことではなく、**「読む → できる → 困った場所から必要な説明へ戻れる」をつなぐこと**を目的としています。公開前の通し検証と実機画像が残る点を、実装済みの範囲と分けて扱ってください。
