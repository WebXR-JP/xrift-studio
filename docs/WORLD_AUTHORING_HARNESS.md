# ワールド制作用ハーネス

ここでいうハーネスは、LLM がワールドを制作するための実行環境と制御の仕組みを指す。Studio 本体が制作状態を保存し、接続した LLM が MCP を通じて編集・撮影・判定を進める。利用者が Studio のソースをクローンしたり、Node.js の実行環境を用意したりする必要はない。

MCP の説明文とツールは、依頼に合ったワールドを制作し、画像で結果を確認できるように整える。具体的な工程と設計図の書式は [ワールド制作スキル](../.agents/skills/xrift-world-direction/SKILL.md) にまとめる。

## 各文書と実装の役割

| 場所 | 残す内容 |
| --- | --- |
| `src-tauri/src/mcp.rs` の instructions | MCP クライアントが最初に読む制作手順と権限 |
| tool の description | 操作の目的、選ぶ基準、操作後の確認、失敗しやすい条件 |
| tool の戻り値 | 現在の状態、診断、次に確認する内容 |
| ワールド制作スキル | 設計図、作業の順序、素材の選び方、完了報告 |
| この文書 | ツールとスキルを変更するときの設計判断 |

外部の制作プロジェクトから接続するクライアントには、このリポジトリのスキルや文書が届くとは限らない。必要な操作説明は MCP の instructions と description にも含める。

## 設計判断

- 床の種類、品質、主役、予算は依頼と設計図に基づいて決める。カタログやツールの数が多いという理由で Terrain や草を選ばせない。
- 素材の入手先に一律の順位を付けない。モデルの形状・容量・ライセンスと、依頼に合うかを確認する。
- 空・環境光・フォグをまとめて確認する。ポストエフェクトは有効にする前後の画像を比較する。
- 回数、三角形数、ライト数などの制作予算は、依頼と公開先に応じて設計図で決める。固定の上限や過去の作例をスキルへ追加して選択肢を狭めない。
- 動きや繰り返しには Script も検討する。Script の承認、ログイン、公開の権限は既存の境界を守る。
- 完了の判断にはスポーン位置と俯瞰からの画像を使う。metrics と document だけで見た目を判断しない。

## 実装による支援

### 制作状態と画像の確認

1. `begin_world_authoring` で設計図と完成条件を保存する。保存先は開いているワールドの `.xrift-authoring/<sceneId>.jsonl`。Git の除外設定も追加する。
   目標を改める場合は `replaceExisting: true` を明示する。以前の状態は履歴に残し、新しい条件で画像確認をやり直す。
2. 再接続時は `get_world_authoring` で目標・確認状況・次の操作を取得する。現在の Scene に対応する保存画像も返る。
3. 編集後、`set_scene_view_camera` でスポーン視点と俯瞰を用意し、それぞれ `capture_scene_view` の `authoringView` に `spawn`、`iso` を指定する。画像は MCP の image content として返るので、LLM に別ディレクトリの読み取り権限を与える必要はない。
4. LLM が両画像と完成条件を見比べ、`review_world_authoring` に合否・根拠・両画像の capture ID を渡す。数値の条件には metrics も照合する。
5. `complete_world_authoring` が現在の Scene に対する確認結果を検証する。未達なら `get_world_authoring` の `uncheckedCriteria` と `nextActions` に沿って続ける。

画像の内容を判断するのは LLM である。Studio は画像の登録と参照、Scene 内容のハッシュ、条件ごとの合否を検査する。Scene を編集した後や画像を撮り直した後は、古い判定で完了できない。スポーンとして登録する視点が実際のスポーン位置に合っているかは、接続した LLM が確認する。

ハッシュでは JSON のキー順と浮動小数点数の往復変換による微小な丸め誤差をそろえる。数値は有効数字12桁で比較し、保存し直しただけで確認済み画像が無効にならないようにする。

履歴には制作状態の更新と、MCP の成功応答時に検出した Scene 変更を追記する。再起動後もファイルから復元する。履歴の同時更新は連番で検出し、破損した行を黙って捨てない。編集自体が成功して履歴の保存だけが失敗した場合は `authoringWarning` を返す。編集を再送せず、状態を確認する。

録画は制作中のワールドの `Recording/` に動画と JSON を保存する。保存先の決定は Studio が行い、MCP に任意の外部パスを指定する機能は設けない。詳しくは [録画](./RECORDING.md) を参照する。

`src/lib/visual-editor/mcp-harness-guard.ts` は、画像を確認せず同じ種類の編集を繰り返したときに警告を返す。Terrain、草、同じ Entity の Transform、同じ Material、Scene 設定の書き込みが、`capture_scene_view` を挟まず 3 回続くと `harness` を付ける。書き込みは拒否しない。カウンターはセッション内だけに持ち、project に保存しない。

外部モデルの検索結果には `polycount` と `dimensionsMm` を含め、取り込む前に予算と比較できるようにする。配置後は接地と Material を画像で確認する。

同じ失敗が続く場合は、説明文、戻り値、制作手順、カタログの構成を調べて直す。過去の失敗談やモデルへの評価を追加する代わりに、判断に必要な情報を返す。

追加機能の候補は [ロードマップ](./VISUAL_EDITOR_ROADMAP.md#今後検討する項目)、ツールの権限と一覧は [MCP ツール](./MCP_EDITOR_TOOLS.md) を参照する。

## 参考にする設計

### CLI とヘッドレス実行

現在の `cli/main.mjs` は Visual から Classic への `convert` を提供する。通常の MCP 操作は、起動中の Studio の Editor を対象とする。コマンドから操作できることと、Studio の描画環境を起動せず操作できることは分けて考える。

| 構成 | 利点 | 費用・制約 |
| --- | --- | --- |
| 起動中の Studio を呼ぶ CLI | シェル、自動テスト、MCP 非対応のクライアントから同じ操作を使える。既存の保存・revision・承認を共有できる | Studio の起動が必要。画像はファイル保存、通常の結果は JSON など、CLI 向けの出力設計が必要 |
| 描画不要の処理をヘッドレス化 | 文書の検査、変換、バッチ処理を CI で動かせる | Editor と同じ変更処理・資産検証・保存トランザクションを使う必要がある |
| 撮影・録画・Play までヘッドレス化 | 無人の映像生成や表示検証が可能になる | WebGL、ブラウザまたは WebView、音声、Script の実行環境が必要。GPU・OS・フォントによる差と権限管理も検証対象になる |

同梱の `xrift-studio-mcp-sidecar` に `tools`、`describe`、`call` を実装した。ツール定義と接続処理は MCP と共有し、すべての操作を同じ保存・revision・承認処理へ渡す。CLI の利用に、このリポジトリのクローンや Node.js は不要。操作例は [MCP ツールの CLI 操作](./MCP_EDITOR_TOOLS.md#cli-から操作する) を参照する。完全なヘッドレス描画は未実装で、無人実行の需要と実行環境を確かめてから別途設計する。

独立した CLI で検討した履歴管理と完了条件を Studio 本体へ移した。実装は `world-authoring.ts` と `world_authoring.rs` に分け、MCP が操作の入口になる。外部の実行ループや特定のモデル接続は同梱しない。

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) は、モデル接続、ツール、セッション記録、実行ループをプラグインとして構成する。[アーキテクチャ資料](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)では、ツール実行の前後に介入する仕組みと、モデルに渡した情報をセッションログから再構成する設計も説明している。

XRift Studio では、この設計を次の判断に役立てた。DeepSeek Harness のコードやパッケージは取り込んでいない。

- モデルやクライアントを変更しても、制作ツールの入出力・権限・検証方法を共通に保つ。
- 操作前の revision 確認と、操作後の結果・画像の確認を、説明文だけでなく実行経路で支える。
- 制作の再開に必要な設計図、操作結果、検証結果を記録する。セッション内の一時的な警告カウンターとは保存目的を分ける。
- 素材の取得や検証方法を追加するときは、役割ごとに交換・拡張できる構成を検討する。
