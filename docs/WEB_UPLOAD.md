# ブラウザからのワールド・アイテム公開

ブラウザ版βには、ワールドとアイテムを XRift へ直接送信する経路がある。パソコン・iPad・スマートフォンから同じ操作で公開を試せる。利用手順は [利用者向けガイド](./guide/publishing.md) にまとめている。ワールドの実送信と XRift 上でのシーン描画は確認済みである。アイテムについては SDK の送信先を隔離した E2E とビルド済みシェルの描画を検証しており、実サービスへの送信・審査・利用は別途確認する。

## 実装の場所

- 経路の分岐: `src/lib/visual-editor/upload.ts`
- ブラウザ実装: `src/lib/visual-editor/web-upload.ts`
- 公開画面: `src/preview/WebUploadDialog.tsx`
- ブラウザのプロジェクトと素材: `src/lib/browser-project-storage.ts`
- ランタイムシェル: `public/xrift-runtime-shell/`

ブラウザ版は作品ごとのビルドを行わず、事前ビルド済みのシェル、`xrift-runtime.json`、素材を組み合わせて公開する。共有シェルは Module Federation で `./World` と `./Item` を公開し、`XriftWorld` と `XriftItem` でマニフェストを描画する。描画・素材・シェーダーには編集画面および Play と同じランタイムアダプターを使う。ワールドの物理処理は `inherit`、アイテムは既存のアイテムアダプターと同じ既定値を使う。送信には `@xrift/sdk` の `client.worlds.upload()` または `client.items.upload()` を使い、アイテムにはワールド専用の physics、camera、items を送らない。Tauri や公式 CLI は実行せず、スクリプトを含む作品はこの経路の対象外とする。

ランタイムや `@xrift/world-components` を変更したときはシェルを再生成する。本番ビルドの実行条件は `AGENT.md` に従う。

```bash
node scripts/build-world-runtime-shell.mjs --out public/xrift-runtime-shell
```

## 認証

XRift の [設定画面](https://app.xrift.net/settings) で、ワールド用の `write:worlds` またはアイテム用の `write:items` 権限付き API キーを発行し、公開画面で入力する。XRift Studio はキーをプロジェクト、IndexedDB、`localStorage`、ログへ保存しない。公開画面には作品の種別に合った権限名を表示し、401 / 403 のエラー時も同じ権限を案内する。

対応ブラウザでは、送信完了画面でユーザーが「APIキーをブラウザに保存」を押したときにパスワード管理機能へ保存を依頼する。保存 API はユーザーがブラウザの確認を承諾する前に完了する場合があるため、その直後にキー選択は呼び出さない。ブラウザ側で保存を終えてから、ユーザーが「保存済みキーを確認」を押して読み戻し、今回送信に使ったキーと一致した場合だけ「保存済み」と表示する。確認の取り消し、読み取り失敗、別のキーの選択時にはキーを保持し、確認または「保存をもう一度依頼」をやり直せるようにする。

ブラウザは初回から無操作で資格情報を渡すとは限らないため、次回の公開時は「保存済みキーを選ぶ」からも読み込めるようにしている。保存はサイトのオリジン単位で行われ、端末間同期はブラウザの設定に従う。

キーは公開画面を開いている間だけメモリ上に保持し、閉じると破棄する。ブラウザの資格情報 API に対応していない場合は、手入力またはブラウザの自動入力を使う。トークンの接頭辞だけで有効性やスコープを判定せず、サーバーから返る 401 / 403 をそのまま伝える。

[Public API v1 の資料](https://docs.xrift.net/public-api/v1) は API キーの認証方法を説明しているが、確認時点のスコープ表には読み取り権限しか載っていない。ここでの公開は Public API v1 の一覧取得ではなく、SDK 0.2.0 の `client.worlds.upload()` と `client.items.upload()` を使うため、資料の表だけで公開権限の有無を判断しない。設定画面でアイテム用の権限を発行できない場合は、実サービスの対応状況を確認する。

## 再開時の判断

CORS と素材の読み取り経路を確認したうえで、実際の API キーを使う試験は既存作品と分離したテスト作品で行う。直接送信が成立しない場合は、プロジェクトを書き出してデスクトップ版から公開する。認証情報を扱う中継サーバーは採用していないため、将来追加する場合は認証と運用の設計を別途行う。

表示の調査では、ブラウザの開発者ツールの Network タブで `xrift-runtime.json` の取得先を確認する。シェルは `import.meta.url` を基準に、作品自身の保存先からマニフェストを読み込む。
