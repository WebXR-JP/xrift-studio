# リリース前 E2E

リリース前には、XRift Studio の主要導線 9 件と、Release ワークフローで指定した回帰テストを確認します。`e2e/release-gate.spec.ts` の `@release-smoke` タグで主要導線を明示しており、追加のテストはワークフロー側で選びます。すべてのテストを自動で必須条件にする運用はしていません。Pull Request や通常の Push では、このリリース用検査を自動実行しません。

## 対象

- 初回セットアップからプロジェクト一覧への遷移
- コード編集 / ビジュアル編集、ワールド / アイテムの 4 通りの作成
- コード編集ワールドの公開情報編集、保存、ローカル実行、停止
- コード編集アイテムのセキュリティチェック
- ビジュアルワールドの Entity 追加、自動保存、Play、Stop
- コード編集とビジュアル編集の公開前確認
- ビジュアルエディターの一時保存失敗からの自動復帰

ガイドの画面幅別検査、全プリセットの描画、個別の Component・地形・スクリプトの詳細検査は、該当機能を変更したときや不具合を調査するときに選んで実行します。リリース時には、次節の一覧にある主要導線と回帰テストを実行します。

実行時は React アプリを Chromium で開き、Tauri IPC と XRift CLI の境界だけをメモリ上のテスト実装に差し替えます。画面表示、状態遷移、入力処理、主要コマンドの組み立ては本番コードを通ります。一方で、Rust 側のファイル操作、実際の Node.js 導入、実 CLI、ネットワーク通信、XRift 側 API はこの E2E の対象外です。

## アップロード禁止境界

テストは次のいずれかを検出すると失敗します。

- シェルコマンドに `upload` が含まれる
- ビジュアル公開処理が `mark_compiler_upload_started` を呼ぶ
- テスト用 IPC に未定義のコマンドが追加される

公開画面では公開要件と最終ボタンの状態までを確認し、最終送信ボタンは押しません。実際のアカウント、プロジェクト、公開先が変更されることはありません。

## リリース時の実行

`.github/workflows/release.yml` では `verify` ジョブと `Release smoke E2E` ジョブを並列に実行し、両方が成功した場合のみ Windows、macOS、Linux のビルドへ進みます。

`verify` ジョブで確認する項目は次のとおりです。

1. リリースタグとアプリバージョンの一致
2. `pnpm typecheck` と `pnpm e2e:typecheck` による型検査
3. `pnpm runtime:shell:check` と VRM 同梱コードの検査・テスト
4. `pnpm cli:test` によるコンパイラフィクスチャと公開ステージング検査
5. 録画の撮影間隔・フレーム取得と使い方ガイドの回帰テスト
6. プレハブの再利用、元の Entity からの反映、個別展開、未反映通知、公開コード生成の回帰テスト

`Release smoke E2E` ジョブは 1 台・1 ワーカーで次を実行します。

1. Chromium と必要なシステム依存の導入
2. `pnpm e2e:smoke`
3. Pi による正式なエディター操作・保存・取り消し・Plan・競合・停止・履歴・権限制御、アイテムの保存・削除、接続・思考量、正式なマテリアル編集・保存・Undo、Skybox 描画・保存の検査
4. UIKit の日本語フォント・公開コード描画、Text の角丸、Entity 右クリックからの制作依頼の検査
5. ブラウザ公開・認証情報・MToon・Audio の検査
6. ギズモ、Hierarchy のドラッグ、描画品質、共通 MToon 描画、Open Brush の個別マテリアル割り当てと輪郭の検査

旧チャット専用の結果設定 UI や依頼候補のテストファイルは Pi 移行に伴い削除されたため、実行対象から外しています。現行の制作導線は `chatgpt-pi-authoring.spec.ts` と `chatgpt-connection-reasoning.spec.ts` で、正式な編集・描画経路は `mcp-material-batch.spec.ts` と `sky-shaders.spec.ts` で確認します。`chatgpt-model-source-integrity.spec.ts` も対象に含めていますが、実 Blender 出力がない環境では SKIP となり、必須の制作検査の代わりにはしません。

`verify` のリリース回帰テストでは、ワークフローが指定した各テストファイルの存在も個別に確認します。Playwright は複数指定のうち一部だけが存在しても成功し得るため、グループ全体の検出件数だけでは判定しません。

型検査は `verify` ジョブで 1 回だけ実行します。コンパイラフィクスチャ、公開ステージング検査、E2E のアップロード禁止境界は常に維持します。

失敗時は `release-e2e-report` という名前のワークフローアーティファクトに、`playwright-report` と `test-results` が保存されます。

## 手動調査

リリース前と同じ範囲をローカルで確認するときは、次のコマンドを実行します。

```bash
pnpm exec playwright install chromium
pnpm e2e:release
```

主要導線だけをブラウザ画面付きで確認したい場合は次を使います。

```bash
pnpm e2e:smoke --headed
```

個別機能の変更では関連するテストファイルを選んで実行します。全件実行も手動で行えます。

```bash
pnpm e2e:test e2e/material-save.spec.ts
pnpm e2e:test
```

日常の変更では `pnpm typecheck` と通常の検証手順に加え、変更した範囲の E2E を組み合わせて確認してください。

## 機能追加時

主要導線を追加または変更したときは、次の点を確認してください。

- 個別機能の回帰テストを対応するテストファイルへ追加したか
- `@release-smoke` を追加する場合、起動・作成・保存・Play・公開前確認を妨げる不具合の検出に必要か、また既存の主要導線と重複していないか
- 新しい Tauri IPC を `src/release-e2e/mock-tauri.ts` に明示したか
- 公開開始より前で停止する境界を維持しているか
- テスト用の成功結果が実機能の成功表示と混同されていないか

ネットワーク制限のある検証環境では、公式の MSDF フォントメタデータを改変せず取得したキャッシュのパスを `XRIFT_E2E_FONT_METRICS_PATH` に指定できます。マテリアル・Skybox 試験はその 1 つの URL だけをキャッシュから返し、その他の通信・描画・エラー検査は変更しません。TLS 検証は無効化しないでください。
