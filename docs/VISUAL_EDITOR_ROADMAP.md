# XRift Studio 対応範囲と段階

設計は [ビジュアルエディター設計](./VISUAL_EDITOR_ARCHITECTURE.md) に置く。この文書は、その設計のどこまでが実際に動き、各段階を何をもって完了とするかを示す。

## 目標

ワールド / アイテムの作成からUploadまでを、XRift Studioだけで進められる制作環境にする。素材の取り込み、シーン編集、動作確認、保存、検査、XRift向け変換を含む。

ビジュアル編集のプロジェクトでは、シーン、素材、マテリアル、プレハブなどの型付きデータを保存・編集する。コード編集export CLIは、この制作データを通常のXRiftコードプロジェクトへ一方向に書き出す。

## 状態の定義

| 状態 | 意味 |
| --- | --- |
| **利用可能** | デスクトップ版の主要導線に接続している。 |
| **検証中** | 実装はある。対応データや実機での受け入れを続けている。 |
| **開発版** | repository内では動く。配布物としては提供していない。 |
| **計画中** | 仕様または実装順序を整理している段階だ。 |

## 対応範囲の境界

ここに挙げるものは、設計上の未対応であり不具合ではない。UIでも同じ内容を表示する。

- OBJの外部MTL / テクスチャはディスク上から自動探索しない。同時に取り込むファイルに含まれたものだけを解決する。
- 付属ファイルを参照するglTF / OBJは、依存ファイルを一緒に取り込んだ場合だけ自己完結GLBへ正規化する。単体で選んだ場合は、依存ファイルの不足を報告して停止する。
- VRMの静的ポーズは保存できる。キーフレーム、クリップ、補間、タイムライン編集は扱っていない。
- 3Dモデルの既存クリップはノードグラフで再生する。ボーン・シェイプキーのキーフレームを作るAnimation authoringは別の計画である。
- ノードグラフのきっかけは開始時、毎フレーム、イベント受信、操作の四つだ。視線や近接に反応するトリガーは無い。視線や近接への反応はXRiftのコンポーネントまたはスクリプトと組み合わせる。
- ノードグラフから次のシーンへ進むことはできない。compilerは開始シーンだけを変換する。遷移の受け皿が公開側にない。`event/send`で名前付きイベントを送るところまでを扱う。
- ノードグラフの実行エンジンはoperation単位で実装する。未対応operationはcanonical JSONに保持したままno-opになる。そのノードと、そこから先のflowは実行されない。対象と理由はEditorと公開側の診断に同じ内容で出す。glTF Object Model pointerを解決するhostがまだない。`pointer/*`は未対応として扱う。
- 空の背景シェーダーはシーンには描画しない。編集中の背景は単色のままだ。見え方は動作確認で確認する。
- Unity固有コンポーネント、シェーダー、スクリプト、Animationを完全には移植しない。対応内容と未対応内容はimport前に示す。
- Open Brushはbrushごとの描画差の検証を続けている。通常のマテリアルoverrideとは扱いを分ける。
- スクリプトの動作確認はアプリと同一realmで動く。module scopeの遮蔽は緩和だ。完全なsandboxではない。
- Webプレビューは制作体験のデモだ。ローカルファイル操作、CLI実行、Uploadはデスクトップ版だけで行う。

## 通常の XRift 開発へ渡す CLI

ビジュアル編集のプロジェクトのmanifestまたはproject rootを指定する。新しいXRiftコード編集のプロジェクトへ一方向に書き出す。

```bash
xrift-studio convert ./my-visual-project --to classic --out ./my-xrift-world
```

repository内では公開時と同じTypeScript / R3Fソースの書き出し、dry-run、未改変exportのupdateを扱う。ビジュアルエディターから既存コード編集のプロジェクトを選ぶ導線まで接続している。書き出し先では公式テンプレートの依存関係だけで`npm install`と`npm run dev`が通る。Runtime JSONと`xrift-studio-runtime`のnpm公開は [ビジュアルプロジェクトをコード編集へ書き出すCLI](./VISUAL_PROJECT_MIGRATION_CLI.md) に記載する。

## 次に満たす条件

1. Open Brush、UnityPackage、OBJ、VRMを実データで受け入れる。保存後の再読込とcompileまで一致させる。
2. 3Dモデル再importへ別元データ選択、付属ファイル付きglTF、変更差分、消失slot参照一覧を追加する。
3. VRM / skinned modelの静的ポーズを実機で確認・改善する。タイムライン用のpose / クリップdata contractを先に固定する。
4. AI連携の認証境界、timeout、付属ファイル同梱、失敗後の再接続をrelease環境で確認する。
5. `xrift-studio-runtime`の音声、パーティクル、動的物理挙動、XRift固有コンポーネントadapterを追加する。コード編集とEditorプレビューの結果を一致させる。静的衝突判定 / 開始位置は実際の実行環境へ接続している。
6. ノードグラフへシーン遷移と`pointer/*`を解決するhostを追加する。書き込み対象は位置・回転・大きさ、Animation、マテリアル、パーティクル、シーンまで接続している。未対応operationの表示はEditorと公開で一致する。
7. マテリアル、動作確認、XRiftのコンポーネント、Uploadを同じビジュアル編集documentから通しで受け入れる。

## 完了判定

ファイルやbuttonの存在だけでは完了としない。各機能は、実データによる操作、保存後の再読込、元に戻す / やり直す、失敗時の復帰、compiler出力まで一致した時に完了とする。CLI移植の完了条件には、dry-runの内容が決定的であること、手書きファイルを既定で上書きしないこと、同じ入力を再実行しても不要な差分を出さないことを含める。

## 今後検討する項目

以下は旧計画から残す検討事項であり、実装済みの機能や確定したAPIではない。着手時に現行の実装と必要性を確認する。

| 分野 | 目的と未決事項 |
| --- | --- |
| カメラの経路再生 | 同じ視点移動を繰り返して検証できるようにする。カメラの保存形式、既存のノードグラフエンジンとの接続、手動操作への復帰、公開対象にするかを決める。再生・停止を同じ場所に置き、未対応の公開経路は診断する。旧案の専用実行器やop名は確定仕様としない。 |
| 制作向けカタログ | 空に合う照明、地形表面、照明器具、建物・家具のセットを拡充する。既存プリセットとレシピを使い、音源・衝突判定の有無を配置前に示す。水や公式コンポーネントをレシピで扱う方法を確認する。 |
| ワールドの仕掛け | 音声Zone、Weather、Trigger Zone、Sit、Door、Scatter、Day / Night Cycle、Reflection Probeを候補として検討する。既存スクリプト・コンポーネントで足りるかを先に確認し、新しい型が必要ならschema・設定・動作確認・compilerを同時に対応させる。 |
| グラフの制作支援 | 再利用できるGraphテンプレート、ステップ実行、ブレークポイントを検討する。保存形式を増やさずcanonical graphを使う。シーン遷移とpointerのhostは上記の未対応範囲を参照する。 |
| 制作方針の引き継ぎ | ワールドの設計図をproject metadataへ保存し、接続するクライアントが変わっても参照できるようにする。保存項目とMCPの返し方を決める。 |

過去の監査にあった保存時のI/O競合、定義の重複、巨大コンポーネントの分割は、当時の行番号や修正コードを再利用せず、現在の実装とfixtureを基準に判断する。保存・取り込みの失敗回復と参照整合性は、引き続き上の完了判定に含める。
