# XRift Studio 対応範囲と段階

設計の詳細は [ビジュアルエディター設計](./VISUAL_EDITOR_ARCHITECTURE.md) に記載している。本書では、その設計のうちどこまでが実際に動作し、各段階を何をもって完了とするかを整理する。

## 目標

ワールドおよびアイテムの作成から公開までを、XRift Studio だけで完結できる制作環境を目指す。素材の取り込み、シーン編集、動作確認、保存、検査、XRift 向け変換までを対象とする。

ビジュアルプロジェクトでは、シーン、素材、マテリアル、プレハブなどの型付きデータを保存・編集する。コードプロジェクト書き出し CLI は、この制作データを通常の XRift コードプロジェクトへ一方向に変換する。

## 状態の定義

| 状態 | 意味 |
| --- | --- |
| **利用可能** | デスクトップ版の主要導線に接続している。 |
| **検証中** | 実装はあり、対応データや実機での受け入れ確認を続けている。 |
| **開発版** | リポジトリ内では動作するが、配布物としてはまだ提供していない。 |
| **計画中** | 仕様や実装順序を整理している段階。 |

| シーン編集 | 利用可能 | Hierarchy、Scene、Inspector、Assets、選択、Transform、親子関係、複製、削除、元に戻す / やり直す。 |

| 音声 | 利用可能 | MP3 / WAV / Ogg / FLAC / AAC / WebM を音声素材として取り込み、Audio Source へ割り当ててシーンと生成物へ保存する。 |

| 色味の調整 | 利用可能 | 露出、コントラスト、彩度などを 1 つのコンポジターで調整する。既定ではオフにしている。 |

| 空と水 | 利用可能 | GLSL で描く空の背景シェーダーと水面マテリアルを公式カタログから追加し、パラメーターで見た目を調整する。どちらもシーンの風とライトを共通入力にする。 |
| 外部リソース | 利用可能 | Poly Haven と ambientCG の CC0 素材、XRift 公式のシェーダー / 地形 / 照明 / Component をアプリ内から追加する。作者とライセンスは素材データと生成物に記録する。 |
| 表現と再利用 | 利用可能 | 基本形状、マテリアル、パーティクル、プレハブ、衝突判定、XRift の Component を作成・配置する。 |
| ノードグラフ | 利用可能 | KHR_interactivity 準拠のグラフをノードエディターで編集する。開始時・毎フレーム・イベント・操作をきっかけに動作し、待機・順次実行・繰り返し・合流・分岐・変数・算術を単一の実行エンジンで処理する。Play と公開先の両方で同じ動作をする。Entity の表示、Transform、アニメーション、マテリアル、パーティクル、音源、ライト、シーンの露出とフェードへ書き込める。1 つの素材に複数グラフを置いてイベントで連携でき、タイムラインで何秒に何が起きるかを確認できる。正規化 JSON と検証処理を UI と MCP で共有している。 |
| スクリプト | 検証中 | スクリプトを TypeScript で書き、Script Component として Entity に付ける。プロパティと参照を宣言して Play で実行する。未承認の元データは内容ハッシュの確認を経てから実行する。同じスクリプトを公開ワールドへ静的 import として出力する。対応範囲は [スクリプト仕様](./SCRIPTING.md) を参照。 |
| 動作確認（Play） | 利用可能 | 編集データと分離した画面で Play / Stop する。ワールドは公式プレイヤー（Rapier の重力・衝突判定・一人称コントローラー・掴み・クロスヘア操作）で確認し、アイテムは単体表示を確認する。Transform・衝突判定・アニメーションの変更は対象 Entity だけを再実行する。実行環境での受け入れ確認を続けている。 |
| コンパイル / 公開 | 利用可能 | ビジュアルプロジェクトの保存、検査、XRift 向け TSX 生成、ステージング、ワールド / アイテムの公開導線を扱う。生成コードは公開テンプレートと同じ `tsc` で検査する。 |
| Open Brush | 検証中 | Open Brush / Tilt Brush 由来の glTF を判定し、`three-icosa` でブラシ表現を読み込む。ブラシごとの受け入れ確認を続けている。 |
| Unity 取り込み | 検証中 | UnityPackage、`.unity`、`.prefab` を解析し、対応するシーン、プレハブ、3D モデル、テクスチャへ変換する。Unity 固有機能の完全互換は対象外。 |
| AI 連携 | 検証中 | アプリ内の接続パネルから MCP サーバーを登録し、シーン読み取り・編集の限定ツールを呼び出す。付属ファイルの同梱を含めた配布確認を続けている。 |
| コードプロジェクトからビジュアル編集への取り込み | 開発版 | ローカルフォルダーまたは HTTPS / git SSH リポジトリを検査し、ワールド / アイテムのエントリーポイントから `src` の相対 import を再帰解決する。静的な R3F、Rapier、XRift の Component、3D モデル / テクスチャ / 音声、空の背景、`ShaderMaterial` をコード実行なしで変換する（一部省略あり）。確定前レビューと確定後の動作確認へ接続し、`group`・ラッパー・ローカルコンポーネントの親子境界を維持する。動的分岐やコレクションは診断対象とする。 |
| ビジュアル編集からコード編集への書き出し | 開発版 | プロジェクト JSON と素材一式を指定し、ランタイム JSON 付きの新規コードプロジェクトへ安全に書き出す。 |
| アニメーションタイムライン | 計画中 | ボーンとシェイプキーのキーフレーム、再生、補間、クリップ保存、XRift 実行環境への出力を扱う。時間軸に沿った演出の組み立てはノードグラフ側で行う。 |

## 対応範囲の境界

以下に挙げる項目は設計上の未対応であり、不具合ではない。UI 上でも同じ内容を案内する。

- OBJ の外部 MTL やテクスチャはディスク上から自動探索しない。同時に取り込んだファイルに含まれるものだけを解決する。
- 付属ファイルを参照する glTF / OBJ は、依存ファイルを一緒に取り込んだ場合だけ自己完結 GLB へ正規化する。単体で選択した場合は、不足している依存ファイルを報告して停止する。
- VRM の静的ポーズは保存できるが、キーフレーム、クリップ、補間、タイムライン編集には対応していない。
- 3D モデルの既存クリップはノードグラフで再生する。ボーンやシェイプキーのキーフレームを作るアニメーション作成機能は別計画とする。
- ノードグラフのきっかけは開始時、毎フレーム、イベント受信、操作の 4 つに限られる。視線や近接に反応するトリガーはなく、必要な場合は XRift の Component やスクリプトと組み合わせる。
- ノードグラフから次のシーンへ遷移することはできない。コンパイラは開始シーンだけを変換し、公開側にも遷移の受け皿がないため、`event/send` で名前付きイベントを送るところまでを扱う。
- ノードグラフの実行エンジンはオペレーション単位で実装する。未対応のオペレーションは正規化 JSON に残したまま何もしない処理（no-op）となり、そのノードと後続のフローは実行されない。対象と理由はエディターと公開側の診断情報に同じ内容で出力する。glTF Object Model ポインターを解決するホストがまだないため、`pointer/*` は未対応として扱う。
- 空の背景シェーダーはシーン編集画面には描画せず、編集中の背景は単色のままにする。見え方は Play で確認する。
- Unity 固有のコンポーネント、シェーダー、スクリプト、アニメーションは完全には移植しない。対応項目と未対応項目を取り込み前に提示する。
- Open Brush はブラシごとの描画差の検証を続けているため、通常のマテリアル上書きとは扱いを分ける。
- スクリプトの Play 実行はアプリと同一の実行領域で動く。モジュールスコープの遮蔽は緩和策であり、完全なサンドボックスではない。
- Web プレビューは制作体験のデモであり、ローカルファイル操作、CLI 実行、公開はデスクトップ版だけで行う。

## 通常の XRift 開発へ渡す CLI

ビジュアルプロジェクトのマニフェストまたはプロジェクトルートを指定し、新しい XRift コードプロジェクトへ一方向に書き出す。

```bash
xrift-studio convert ./my-visual-project --to classic --out ./my-xrift-world
```

リポジトリ内では、公開時と同じ TypeScript / R3F ソースの書き出し、dry-run、未改変の書き出し先に対する更新を実装している。ビジュアルエディターから既存コードプロジェクトを選んで書き出す導線も接続済みで、書き出し先では公式テンプレートの依存関係だけで `npm install` と `npm run dev` が通る。ランタイム JSON と `xrift-studio-runtime` の npm 公開については [Visual Project Classic Export CLI](./VISUAL_PROJECT_MIGRATION_CLI.md) に記載している。

## 次に満たす条件

1. Open Brush、UnityPackage、OBJ、VRM を実データで受け入れ、保存後の再読み込みからコンパイルまでを一致させる。
2. 3D モデルの再取り込みに、別の元データ選択、付属ファイル付き glTF、変更差分、消失したスロット参照の一覧を追加する。
3. VRM およびスキニング済みモデルの静的ポーズを実機で確認・改善する。タイムライン用のポーズ / クリップのデータ契約を先に固定する。
4. AI 連携の認証境界、タイムアウト、付属ファイル同梱、失敗後の再接続をリリース環境で確認する。
5. `xrift-studio-runtime` に音声、パーティクル、動的物理挙動、XRift 固有 Component のアダプターを追加し、コードプロジェクトとエディタープレビューの結果を一致させる。静的衝突判定と開始位置は実際の実行環境へ接続済み。
6. ノードグラフにシーン遷移と `pointer/*` を解決するホストを追加する。書き込み対象は Transform、アニメーション、マテリアル、パーティクル、シーンまで接続済みで、未対応オペレーションの表示もエディターと公開で一致している。
7. マテリアル、Play、XRift Component、公開を、同一のビジュアルプロジェクトから通しで受け入れ確認する。

## 完了判定

ファイルやボタンが存在するだけでは完了としない。各機能は、実データでの操作、保存後の再読み込み、元に戻す / やり直す、失敗時の復帰、コンパイラ出力まで一致した時点で完了とする。CLI 書き出しの完了条件には、dry-run の結果が決定的であること、手書きファイルを既定で上書きしないこと、同じ入力を再実行したときに不要な差分が出ないことも含める。

## 今後検討する項目

以下は旧計画から引き継いでいる検討事項であり、実装済みの機能や確定した API ではない。着手時に現行実装と必要性を改めて確認する。

| 分野 | 目的と未決事項 |
| --- | --- |
| カメラの経路再生 | 同じ視点移動を繰り返して検証できるようにする。カメラの保存形式、既存ノードグラフエンジンとの接続、手動操作への復帰、公開対象に含めるかを検討する。再生・停止を同じ場所に置き、未対応の公開経路は診断に出す。旧案の専用実行器やオペレーション名は確定仕様としない。 |
| 制作向けカタログ | 空に合う照明、地形表面、照明器具、建物・家具のセットを拡充する。既存のプリセットとレシピを使い、音源や衝突判定の有無を配置前に示す。水や公式 Component をレシピで扱う方法を確認する。 |
| ワールドの仕掛け | 音声ゾーン、Weather、Trigger Zone、Sit、Door、Scatter、Day / Night Cycle、Reflection Probe を候補として検討する。既存のスクリプトや Component で対応できるかを先に確認し、新しい型が必要ならスキーマ・Inspector・Play・コンパイラを同時に対応させる。 |
| グラフの制作支援 | 再利用できるグラフテンプレート、ステップ実行、ブレークポイントを検討する。保存形式を増やさず正規化グラフを使う。シーン遷移とポインターのホストは上記の未対応範囲を参照する。 |
| 制作方針の引き継ぎ | ワールドの設計図をプロジェクトメタデータに保存し、接続するクライアントが変わっても参照できるようにする。保存項目と MCP の返却形式を決める。 |

過去の監査で挙がっていた保存時の I/O 競合、定義の重複、巨大コンポーネントの分割については、当時の行番号や修正案をそのまま再利用せず、現在の実装とフィクスチャを基準に判断する。保存・取り込みの失敗回復と参照整合性は、引き続き上記の完了判定に含める。
