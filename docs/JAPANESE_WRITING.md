# 日本語表記と用語ガイド

XRift Studio の画面文言、ユーザーガイド、技術ドキュメント、PR・コミットメッセージを書くときの表記と文章のルールをまとめています。

## 文章の基本方針

人が読んでそのまま頭に入る、自然で読みやすい日本語を心がけます。

### 避ける表現と書き換えの例

1. **日本語の文章中に一般の英単語をそのまま混ぜない**
   - 画面上のラベル、固有名詞、コード内の識別子（バッククォートで囲む）以外の一般語は日本語で書きます。
   - 避けたい例: `ビジュアルproject`、`元データfile`、`参照field`、`代替tool`、`公式sample`、`別transaction`
   - 望ましい例: `ビジュアルプロジェクト`、`元データファイル`、`参照フィールド`、`代替ツール`、`公式サンプル`、`別トランザクション`

2. **直訳調・硬すぎる定型表現を使わない**
   - 英語の逐語訳のような不自然な動詞や名詞の多用を避けます。
   - 例: 「〜を保つ」ばかりを繰り返さず、文脈に合わせて「そのまま残す」「維持する」「壊さない」などを使い分けます。
   - 例: 「実描画画像」「実画面」「正本」「改稿」「逐語録」のような見慣れない表現は、ユーザー向け文書では「実際の描画」「実際の画面」「元データ」「書き直し」「書き起こし」などに言い換えます。

3. **ユーザーガイドに内部仕様や防衛的な注記を詰め込まない**
   - ユーザーガイド（`README.md` や `docs/guide/`）では、利用者がやりたいことと必要な注意点に焦点を当てます。
   - 「空の見出しは出しません」「未完成の再生枠はありません」「同じ文は重ねて表示しません」といった開発者目線の実装メモを、そのままマニュアルに書かないでください。
   - 1 つの段落に話題を詰め込みすぎず、手順は番号付きリスト、設定項目の比較は表、注意点は短い段落や箇条書きに分けます。

4. **PR タイトル・本文・コミットメッセージは簡潔に自然に書く**
   - 主語や目的語の直後に不自然な読点を入れたり、長い修飾節を 1 文に押し込んだりしないでください。
   - 避けたい例:
     - `数値の欄が、遅れて届いた保存結果で入力中の文字を置き換えないようにする`
     - `GLBのインスタンスごとの独自属性を、編集・Play・公開で同じ値としてシェーダーへ届ける`
     - `ランタイム契約を上げ、ブラウザ公開用のランタイムシェルを作り直す`
   - 望ましい例:
     - `数値入力中に遅れて届いた保存結果で入力値が上書きされないよう修正`
     - `GLB のインスタンスごとのカスタム属性を編集・Play・公開のすべてでシェーダーに渡す`
     - `ランタイムの契約バージョンを上げ、ブラウザ公開用ランタイムシェルを再生成`

5. **文体をそろえる**
   - ユーザーガイド、`README.md`、`DEVELOPMENT.md`、`AGENT.md`、PR 本文は丁寧語（です・ます調）で統一します。
   - 技術仕様書（`docs/` 配下の設計書など）は常体（だ・である調）または丁寧語（です・ます調）のどちらかに文書内で統一し、途中で突然「〜だ。」が混ざらないようにします。

## 画面名と基本用語

画面名は「ビジュアルエディター」「コードエディター」とします。操作は「素材を配置する」「コードを編集する」、プロジェクトの種類は「コードプロジェクト」のように、画面名・操作名・データ名を区別して案内します。

ワールドの実行・終了ボタンは画面表記に合わせて「Play」「Stop」を使います。機能の説明としては「動作を確認する」などと書き、録画や音声の停止操作と混同しないようにしてください。

| 名前 | 役割 |
| --- | --- |
| Entity | シーンに配置する個々のオブジェクト |
| Inspector | 選択した Entity や素材の設定を編集するパネル |
| Hierarchy | シーン内の Entity 一覧と親子関係を表示するパネル |
| Assets | 3D モデル・画像・音声・マテリアルなどを管理するパネル |
| Components | Entity に追加する機能の一覧・追加メニュー |

- 個別の機能には「Component」、データ全般には「素材」を使います。パネルを案内するときは `Assets` や `Inspector` のように画面上の表示名をそのまま書きます。
- マテリアル、テクスチャ、ノードも制作で使う基本用語です。意味が分かりにくい用語はユーザーガイドで補足します。
- Component 名は「Add Component」の登録名に合わせます。`Mesh Renderer`、`Rigid Body`、`Box Collider`、`Mesh Collider`、`Transform` および XRift 公式 Component の名前は、Inspector・操作メニュー・通知でも同じ英語名を使い、効果や使い方を日本語で説明します。

## 専門用語と日本語の使い分け

他の 3D 制作ツールや仕様書で広く使われている用語は、画面の主ラベルにそのまま残します。英語名をツールチップだけに隠さないでください。初めて使う人にも役割が分かるよう、必要な場所には短い日本語の説明を添えます。

| 用語 | 効果・用途 |
| --- | --- |
| Normal Map | 陰影で細かな凹凸を表す画像。メッシュの形や輪郭は変わらない |
| Skybox / Skybox Texture / Skybox Shader | 背景、背景画像、背景の色や動きを描くシェーダー |
| IBL | 環境画像を照明や反射の計算に使う仕組み |
| Bloom | 明るい部分の光をにじませる画面効果 |
| SSAO | 接地部分や隙間に陰影を加える画面効果 |
| Fog | 遠景をかすませる効果 |
| Ambient Light | シーン全体を均一に照らす環境光 |
| Color Grading | 画面全体の明暗差や色味を調整する効果 |

- 設定項目名には `Skybox` や `Bloom` などの専門用語を使い、効果の説明は日本語で書きます。
- 「上空の色」「地平線の色」などの色の名称や、「追加」「削除」といった操作名は自然な日本語を使います。一般語まで機械的に英語へ置き換えないようにしてください。
- 見た目が似ていても別の機能であるものは、説明をはっきり分けます。たとえば、SkyboxとIBL、Normal Mapと形状の変形、Occlusion MapとSSAO、EmissiveとBloomはそれぞれ別の設定です。ライトを含まない発光プリセットを「周囲を照らすライト」のように説明しないでください。
- Inspector、シーン設定、カタログ、ノードの選択肢、通知、ユーザーガイドの間で名称をそろえます。入力形式・単位・条件がある項目では、それぞれを短く明記します。

### Node Graph の表記

- Node Graph では、Node・Category・Port・型の名前を英語で表示します。`On Start`、`Branch`、`Sequence` のように他のツールや仕様書でも使われる名前を維持し、動作とつなぎ方を日本語で説明します。
- 番号付きの Port は、入力・出力とも 1 から始まる数字で表示します。追加・削除・整列などの操作ボタンは日本語で案内します。
- 新規作成した Graph の既定名は `Main` や `Animation` などの英語名にそろえます。利用者が付けた名前は、保存済みの `graph.name` をそのまま表示します。レシピ名や操作ボタンは日本語で表示します。
- 表示文を見直すときに、Node の `op`、Port の ID、型の識別子、保存形式は変更しないでください。

## マテリアルの表記

- 項目名は glTF の英語名を基準にします。`Base Color`、`Metallic`、`Roughness`、`Clearcoat`、`Iridescence`、`Transmission` などは、そのまま英語名で表示してください。Blender や Unity の用語を参考にする場合も、シェーダーごとの意味の違いを確認した上で扱います。
- 見出しは英語名を主とし、必要であれば意味が伝わる短い日本語を添えます。`MToon` や `Bloom` のように定着している名称には、不自然な読み方や日本語の補足を付けません。
- 子項目では数値の向き、単位、前提条件を分かりやすく説明します。ボタン・案内文・エラーメッセージは日本語で書きます。
- `Clearcoat` には「透明な上塗り」、`Iridescence` には「薄膜の虹色反射」のように効果を伝える短い説明を添えられますが、英語の項目名自体は残してください。
- 似ている項目を同じ意味として扱わないでください。`Base Color` と `Diffuse Color`、`Roughness` と `Smoothness`、`Alpha` と `Transmission` は別物です。また、`Volume` の材質の厚みと `Iridescence` の膜厚（単位は nm）も別の設定です。
- 標準マテリアルの `Alpha` と、動作中に変更するマテリアルの `Opacity` は対象が異なります。API の識別子を維持しつつ、それぞれの用途を説明します。音声の `volume` は「音量」と表記し、マテリアルの `Volume` と区別します。
- 拡張マテリアルの見出しと説明は `material-extension-registry.ts` にそろえます。単体編集、複数選択、ノードのマテリアル項目、ユーザーガイドでも同じ名前を使い、拡張 ID は見出しのツールチップに残します。

## 操作名・条件・安全面の注意点

- ガイドに書く操作名は、必ず現在の画面ラベルに合わせてください。たとえば、プレハブの更新ボタンは「プレハブに反映」、調整パネルは「Inspector」と書きます。
- ノードの旧名を別名テーブルや検索互換用として追加しません。検索対象には現在の表示名、説明文、操作 ID を使います。
- ファイルをプロジェクトへ入れる操作は「追加」「取り込み」、XRift へ送信する操作は「公開」と書きます。Git リポジトリからのコピーは GitHub の fork と混同しない表現にします。一般的な案内では「AIクライアント」「インストール」「プロジェクト」と書き、進捗 ID の `npm-install` などは表示ラベルだけを日本語にします。
- ノードの説明では、実行のタイミングとつなぎ先を正確に書きます。`Set Delay` で待機後に実行したい処理は `Done` につなぎます（`Out` は待機開始直後に進みます）。`Sequence` も各処理の完了を待たずに次へ進みます。実装の挙動と説明が一致しているか確認してください。
- 入力条件、単位、数値の向き、共有素材への影響、未保存の変更が失われる操作、利用条件などの大事な情報は省略しないでください。必要な入力条件は、入力前から見える場所に示します。
- エラー案内では分かっている原因と次の操作を具体的に示し、原因が特定できないことは断定しません。送信結果が不明な場合も、確認先と二重送信を防ぐ手順を必ず残します。
- API 名、ノードの `op`、ポート ID、JSON キー、保存済み ID、URL、コマンドは書き換えないでください。第三者のライセンス原文や過去の検証記録の事実関係も維持します。

## 変更後の確認

- 画面文言を変更したら、`README.md`、ユーザーガイド（`docs/guide/`）、`docs/guide/manifest.json` との整合も確認してください。起動、新規作成、取り込み、編集、Play、保存、公開、終了の各操作に加え、未選択・処理中・成功・失敗・取り消し時の表示も対象です。
- `node --test scripts/japanese-copy.test.mjs scripts/ui-flow-copy.test.mjs` で、用語・検索・説明・保存形式・リンクの整合を確認できます。画面のソースコードを変更した場合は `pnpm typecheck` も実行してください。
- 実際の画面では、文字切れ、不自然な改行、空の枠、エラー時の案内を目視で確認します。検証できた範囲と未確認の範囲は PR の説明に明記してください。

## 制作チャットの文章方針

- 制作チャットの画面では「外部拡張」ではなく「制作に使う追加機能」と表記します。「思考量」はそのまま使い、API の `reasoningEffort` などの識別子は変更しません。
- 制作チャットの応答文には、Yomiyasu 由来の文章方針を適用しています（原文・ライセンス・適用範囲は `packages/studio-pi/resources/yomiyasu/` を参照）。
- 回答本文だけでなく、進捗表示、制作プラン、確認質問と選択肢、完了報告、履歴、入力案内、エラー表示も同じ方針で整えます。モデルが生成する文章は共通のシステム指示で、固定の表示文はソースコードとガイド側で管理します。利用者の入力や外部サービスのエラー原文を一律に書き換えたり、校正のためだけにモデルを追加呼び出ししたりはしません。
