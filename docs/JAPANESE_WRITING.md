# 文章と用語のルール

エディターの名前は保ち、操作に必要な説明だけを短く書きます。日本語へ一律に置き換えることはしません。

## 残す表記

制作方式や画面の名前は「ビジュアルエディター」「コードエディター」に統一します。「ビジュアル編集」「コード編集」を画面名の代わりに使いません。操作は「素材を配置する」「コードを編集する」、データは「コードプロジェクト」のように、画面の名前と区別します。

| 表記 | 用途 |
| --- | --- |
| Entity | シーンに配置するもの |
| Inspector | 選択したものを編集するパネル |
| Hierarchy | Entityの階層を表示するパネル |
| Assets | モデル、画像、音声などを管理するパネル |
| Components | Entityに追加する機能の一覧・追加メニュー |

説明文で個別の機能を指す場合は「Component」を使います。「素材」はデータ一般を指すときに使い、パネルを案内するときは「Assets」と書きます。「設定」は操作や項目の総称で、Inspectorの別名には使いません。

マテリアル、テクスチャ、ノードなど、制作に必要な用語も残します。用語の定義は利用ガイドにまとめ、各画面で繰り返し説明しません。

## 専門用語と日本語の使い分け

他の制作ツールや仕様書でも使われる名前は、画面で見える主ラベルに残します。英語名をツールチップだけに隠さないでください。初めて使う人には、短い日本語で効果や操作を説明します。

| 名前を残す | 説明に使う日本語 |
| --- | --- |
| Normal Map | 陰影で細かな凹凸を表す。メッシュの形や輪郭は変わらない |
| Skybox / Skybox Texture / Skybox Shader | 背景、その画像、その色や動きを描くマテリアル |
| IBL | 画像を照明や反射に使う |
| Bloom | 明るい部分の光をにじませる |
| SSAO | 接地部分や隙間に陰影を加える |
| Fog / Ambient Light / Color Grading | 遠景をかすませる／全体を均一に照らす／明暗差や色味を調整する |

「空の背景」をSkyboxの別名にしたり、「光のにじみ」をBloomの項目名にしたりしません。一方、実際の色を選ぶ「上空の色」「地平線の色」、ボタンの「追加」「削除」、案内文は日本語のままで構いません。一般語まで機械的に英語へ置き換えないでください。

SkyboxとIBL、Normal Mapと形状の変形、Occlusion MapとSSAO、EmissiveとBloomは別の設定です。似た見た目になる場合でも、同じ名前や説明にまとめません。プリセットにライトが含まれない場合は、発光する形を「周囲を照らすライト」と説明しないでください。

Inspector、シーン設定、カタログ、ノードの選択肢、通知、利用ガイドで名前を揃えます。説明は必要な場所にだけ置き、入力形式・単位・条件は効果の説明と分けて短く示します。

## マテリアルの表記

項目名はglTFの英語を基準にします。`Base Color / Metallic / Roughness / Clearcoat / Iridescence / Transmission`などを独自の日本語名に置き換えません。Blender・Unityの名前も参照しますが、シェーダーごとの意味の違いを優先します。

見出しは英語名を主にし、カタカナの読み方や短い日本語を小さく添えます。子項目では英語名を繰り返し翻訳せず、数値の方向・単位・必要条件を日本語で説明します。ボタン、案内、エラーまで英語に統一する方針ではありません。

`Clearcoat`を「透明な上塗り」、`Iridescence`を「薄膜による色の変化」という項目名にはしません。その日本語は効果の説明に使います。`Base Color`と`Diffuse Color`、`Roughness`と`Smoothness`、`Alpha`と`Transmission`を同じものとして扱わないでください。`Volume`の材質の厚みと`Iridescence`の膜厚（nm）も区別します。

標準マテリアルの`Alpha`と、動作中のマテリアルに対する`Opacity`は、編集する値が違うため名前も分けます。APIの識別子は変えず、説明で用途を案内します。技術用語を含むという理由だけで、文章中の一般語や音量の`volume`まで機械的に置き換えないでください。

拡張の見出しと読み方は`material-extension-registry.ts`を参照します。単独編集、複数選択、ノードのマテリアル項目、利用ガイドで名前を揃えます。拡張IDは見出しのツールチップにも残します。

## 説明を減らす

見出しやボタン名で分かる説明は削除します。「ここで確認できます」「保存データに記録されます」「内部のrendererで描画しています」など、次の操作に関係しない案内は表示しません。段落を削除するときは、空の枠や余白も残さないでください。

操作や数値の説明は、原則1〜2文にします。「できます」を繰り返さず、条件と結果を近くに置きます。説明を短くするために専門語を増やしたり、意味を省いたりしないでください。

| 避けたい説明 | 書き方の例 |
| --- | --- |
| 利用できるテクスチャがありません。素材へ画像を読み込んでください。 | Assetsに画像を追加してください。 |
| マテリアルのパラメーターを調整できます。 | 0で反射がくっきりし、1で反射がぼやけます。 |
| 元のファイルを保持したまま編集画面と実行環境の両方で変換後のファイルを使います。 | 元ファイルは残し、変換したファイルを使います。 |

## 省略しない説明

入力条件、単位、数値の方向、共有素材への影響、未保存の変更が失われる操作、利用条件は残します。エラーは、分かっている原因と次の操作を示します。原因が不明なときは推測で断定しません。必要な条件をプレースホルダーやツールチップにだけ隠さないでください。

ノードは、いつ実行するか、どこへつなぐかを説明します。「指定時間待つ」の待機後は「完了後」へ接続します。「順に実行」は、各処理の完了を待ちません。説明は実装と照合してください。

案内から別の機能へ誘導するときは、現在の画面にある名前を使います。旧ノード名の別名表や検索互換は追加しません。検索対象は現在の表示名・説明・操作IDです。

## 操作の流れで確認する

起動、新規作成、取り込み、編集、動作確認、保存、公開、終了の順に確認します。通常表示だけでなく、未選択・処理中・成功・失敗・取り消しの案内も対象です。

- ファイルをプロジェクトに入れる操作は「追加」「取り込み」、XRiftへ送る操作は「公開」と区別します。GitからのコピーをGitHubのforkと呼びません。
- 操作先は画面のラベルどおりに書きます。「設定で設定」ではなく「Inspectorで調整」、「更新」ではなく実際のボタン名「プレハブに反映」とします。
- 一般的な操作説明に`client`、`install`、`project`などを混ぜません。「AIクライアント」「インストール」「プロジェクト」と書きます。`npm-install`などの進捗IDは変えず、表示だけ日本語にします。
- ラベルは接続先の値と照合します。音声の`volume`は「音量」で、マテリアルの`Volume`とは別です。名前が同じ変数を一括翻訳しません。
- 入力条件は入力前から表示します。送信結果が不明なときは成功・失敗を断定せず、確認先と二重送信を避ける手順を残します。

## 変更しないもの

API名、ノードの`op`、接続口のID、JSONキー、保存済みID、URL、コマンドは翻訳しません。表示名の整理と保存形式の変更を混ぜないでください。第三者のライセンスや過去の検証結果も改変しません。

画面を変更したら、README、利用ガイド、`src/lib/wiki-config.ts`の案内も揃えます。内部実装の詳しい説明は開発文書へ置きます。

## 確認する

`node --test scripts/japanese-copy.test.mjs scripts/ui-flow-copy.test.mjs`で用語、検索、説明、保存形式、文書参照を確認します。別途`pnpm typecheck`を実行し、実画面で文字切れ、改行、空の枠、エラー時の案内を確認してください。自動検査だけで画面確認を済ませたことにはしません。
