# 実装時に守る契約

変更に関係する節だけを参照する。本文中のパスはリポジトリルートからの相対パスである。

## UI と表記

- 操作を追加・変更するときは [UX 原則](./UX_PRINCIPLES.md) を確認し、操作前・処理中・成功時・失敗時・戻り先を設計する。完了後に次の操作へ進める表示も用意する。
- UI を追加・変更するときは、同じ画面にある既存コンポーネント（モーダル、ダイアログ、ボタン、通知）の実装を先に確認し、既存のレイアウト、角丸、余白、色トークン、フォーカス表現を再利用する。独自の判断で新しい配色や強い装飾を加えない。既存パターンと変える場合は、理由を UX 原則または機能仕様に記録する。
- 動きや状態遷移を変更する場合は [機能別の操作・状態設計](./UX_INTERACTIONS.md) で該当の機能 ID と `MI-xx` を確認し、追加する機能の状態遷移を先に記録する。既存項目に当てはまらない動きを追加するときは、目的、開始条件、時間、終了状態を追記する。
- 新規作成・起動・公開・更新フローでは、成功トーストだけで終わらせない。作成物、起動 URL、公開 URL、更新後のバージョンなど、結果そのものへ移動できる表示を画面に残す。
- ワールドをアップロードする前に、`xrift.json` のタイトル・説明・サムネイルがテンプレートのままではないか確認する。未編集の項目があればアップロードを開始せず、編集・保存・再確認からアップロードまでを一続きの導線でつなぐ。
- 一覧画面では、新規作成の入口を常に見つけやすい位置に置く。各項目には識別しやすい情報を載せ、空状態・読み込み中・読み込み失敗の表示を用意する。削除や一時的な操作を除き、選択中の対象や編集中の内容を不用意に消さない。
- 進行中の処理には実行中表示と二重操作防止を付ける。失敗時は次の行動や確認先を示し、処理中に安全でない中断ができるようには見せない。
- 白とグレーを基調にし、ブランド色は主操作、成功後の URL、更新対象など注目すべき箇所に限定して使う。状態変化や画面遷移には、短く控えめな動きを使う。
- Markdown 文書、画面文言、コミットメッセージに絵文字は使わない。アイコンだけに意味を持たせず、主要操作には読めるラベルか `title` を付ける。
- 新しい画面は、まずブラウザで動く React の状態・表示として作り、Tauri 固有の処理を小さな IPC ラッパーへ分離する。
- XRift のワールド内 Component、公式 Component、3D アセットの見た目を SVG、CSS 図形、DOM の疑似サムネイルで代替しない。編集画面・Play・カタログのいずれも、`@xrift/world-components` 本体または同じ Three.js / React Three Fiber の描画経路を使う。
  - 公式 Component がコンテキストを必要とする場合は、Studio 用の Provider ブリッジを用意し、独自の古いデザインを作り直さない。
  - Component 自体が子要素だけを包むラッパーの場合は、公式サンプルの WebGL 子要素を表示する。
  - 実際に描画できない対象は架空の見た目を作らず、未対応の理由を明示する。
- ネイティブ API が使えないブラウザプレビューでは、成功しているように見せるモックを実機能と混同させない。サンプル・デモであることを画面上に明示する。
- 新しい Component を Add Component メニューへ追加するときは、同じ作業内で Inspector からの削除導線も用意する。`ComponentCard` の `remove` を使い、削除ハンドラは `VisualEditorPrototype` の `handleRemoveComponent` を通す。
  - `Transform` のように削除できない Component は、押しても削除できない理由が分かる通知を返す。
  - Inspector に専用 UI を持たない種別でも共通カードを表示し、画面から見えない Component を残さない。追加できて外せない状態にすると、Entity ごと作り直すしかなくなる。

## 編集・Play・公開の描画を揃える

Studio で制作中に見えている素材と動作を、そのまま公開先でも再現する。実物のモデル、シェーダー、テクスチャ、公式 Component を使って開発・確認し、見た目だけを似せた代替表示を完成品として扱わない。

- 形状、材質、色空間、テクスチャの読み込み、照明、露出、アニメーションには同じ実行コードと値を使う。共通の描画処理は `packages/xrift-studio-runtime/src/` に置き、エディターから参照するとともに公開物へ同じソースを同梱する。生成側に別の実装や既定値の表を持たせない。
- コンパイラと環境別アダプターは、シーンの組み立て、素材 ID から配信 URL への解決、コンテキストの接続を担う。公開時だけ通常の材質へ置換したり、色や寸法を補正したり、数値を丸めたりしない。対応するシェーダーや依存素材を正しく読み込めるよう、描画経路そのものを修正する。
- 公開時には編集画面で使っている画像をそのままコピーする。縮小・圧縮・形式変換を作者が選ぶ場合は、制作中に適用結果を表示し、確認済みの素材を公開する。公開のタイミングで別の画像へ自動変換しない。
- シェーダーや素材を読み込めない場合、別物を表示して読み込み成功と扱わない。参照元とエラーを保持したまま原因を修正する。警告や公開前チェックを増やすだけで描画経路の修正を終えない。
- グリッド、ギズモ、選択枠などの編集補助は、作品の材質・透明度・形状に影響させない。軽量表示など作者が選んだ表示品質の差は明示し、保存データや公開結果へ混ぜない。
- 描画に関わる変更は、編集画面と実際に生成した公開コードの両方で確認する。比較には同じ素材、カメラ、照明、描画品質、再生状態・時刻を使う。別々に調整して似せた画像や、コンパイラの文字列検査だけを一致の根拠にしない。検証した対象・条件と未確認の経路を区別して記録する。
- ライトベイクは編集中に実行し、結果を `lightmap` 種別のアセットとして保存する。公開時に焼き直さず、アセットの 2 ファイルをそのままコピーする。適用処理は `packages/xrift-studio-runtime/src/lightmap-apply.ts` に置き、エディターと公開物で共有する。Mesh の数え方、UV2 の形式、焼く光の意味を変えるときは、[ライトベイクの仕組み](./LIGHT_BAKE.md) と `light-bake.fixture.ts` を同じ変更で更新する。

既存実装には未共通化の部分もある。描画の差を見つけたら共通ソースへ統合し、個別の置換や補正を加えたり、既存作品の保存値を一括変更したりして帳尻を合わせない。

## Component・Graph・公開物

- シーン設定画面に項目を追加したら、同じ作業でビューアーごとの実行時変更を許可するか決める。
  - ポストエフェクト、フォグ、環境光、Skybox、露出、視野角など見た目に関わる項目は、`packages/xrift-studio-runtime/src/script/scene-runtime.tsx` のブリッジに上書き口を追加し、Interactivity Graph の `scene` ターゲットと `ctx.viewer` の両方から書き込めるようにする。
  - シーン設定は全ビューアー共通のため、個別に上書きできなければ、処理の重い端末だけを除外できず全体の品質を下げることになる。書き込みは常にクライアントローカルとし、他のビューアーへは同期しない。Stop と再入室で元のシーン設定へ戻す。
  - ギズモ、グリッド、エディター背景など編集時だけの項目は対象外とし、その理由を `docs/KHR_INTERACTIVITY_EDITOR.md` に記録する。
- Interactivity Graph から Entity の Component を書き換えられるようにするときは、Play と公開先が同じランタイムブリッジを通ることを先に確認する。ブリッジがない Component は、先にブリッジを追加してからプロパティを公開する。Inspector の Component 一覧に出るのに「プロパティを変える」の対象に出てこない Component を残さない。対象に含めない判断をした場合は、理由を `docs/KHR_INTERACTIVITY_EDITOR.md` の「What a trigger can write」に記録する。
- アセット ID や文字列など数値以外の値を Graph のプロパティにする場合は、`configuration` に置き、value ソケットを使わない。KHR_interactivity には string 型がなく、アセットや文字列は補間できないため duration も適用しない。アセットを参照するプロパティを追加したら、同じ作業でグラフから Component の `assetReferences` を導出し、コンパイラが依存素材を公開物へ含められるようにする。導出時はグラフ内の全アクションノードを走査する。`xrift/onInteract` から辿るだけでは、自動開始するグラフの依存素材を記録できない。
- エディターに新しい操作を追加したら、同じ作業単位で MCP ツールも追加する。Inspector やツールバーからしか操作できない機能は、AI クライアントから扱えない。手順とサーフェスごとの権限は `docs/MCP_EDITOR_TOOLS.md` に従う。公開しない判断をした場合は、理由を同じ文書の「意図的に公開していない操作」へ記録する。
- 公開したワールドが配信できるのはワールド直下のファイルに限られる。`public/` 配下のサブディレクトリは公開物に含まれないため、アセット、デコーダー、フォント、ランタイムマニフェストはすべて `public/` 直下に平坦に配置し、ファイル名で衝突を避ける。詳細は `docs/SCRIPTING.md` の「公開物はワールド直下にしか置けない」を参照する。

### MToon・VRM 同梱ソースの扱い

MToon・VRM の生成コードには、固定バージョンの `@pixiv/three-vrm` 配布ソースとライセンスを同梱する。SDK が難読化と誤判定する既知の内部バインディングだけを構文解析で改名し、公開 API、`constructor.name`、描画・読み込み処理は変えずに維持する。ブラウザ公開のランタイムシェルでも、隔離した公式テンプレート内のエイリアス経由で同じ配布ソースを使う。

- 描画コードを更新したときはランタイム契約を更新し、`node scripts/build-world-runtime-shell.mjs` でシェルを再生成する。
- `node scripts/prepare-readable-three-vrm.mjs --check` で原本の SHA-256 と生成物を照合する。
- 依存を更新したときは、再生成と `node --test scripts/readable-three-vrm.test.mjs` に加え、隔離した生成物の実ビルド、公式 CLI 検査、編集画面との描画比較を行う。セキュリティ検査も通常のルールで実行する。

## Scene の更新と描画性能

- Entity 単位の描画コンポーネントには `SceneDocument` 全体を渡さない。Scene View の Entity ツリーは `scene-entity-tree-store.ts` で Entity ごとに更新を購読し、全ノード共通の値だけをコンテキストから受け取る。ノードのプロパティには、親 Entity から決まる `entityId`、`inheritedRigidBody`、`ancestorEnabled` のみを渡す。
  - シーン全体を親から渡すと、1 つの Entity を編集しただけで全 Entity の props が変わり、`memo` で再描画を抑止できない。
  - Entity 単体を親から渡す構成でも、Component を追加した際に祖先 Entity が変わらず、`memo` された親が再描画を止めて子孫へ変更が届かない。各 Entity が直接更新を購読する構成を維持する。
- `SceneDocument` を更新するときは、変更していない Entity のオブジェクト参照を維持する。`editor-session.ts` では `{ ...scene.entities, [id]: { ...entity } }` の形を守り、`prefab-resolver.ts` ではプレハブを展開した Entity だけを差し替えて、それ以外は同じ参照を返す。全 Entity を複製すると `memo` も `useMemo` も参照一致を判定できず、シーン全体が再描画される。
- Entity ツリーの共有コンテキストには、すべての Entity が描画に使う値だけを置く。選択中の Entity 一覧のように一部ノードしか参照しない値は、`scene-entity-tree-context.tsx` の専用コンテキストへ分離し、参照側が `useSceneSelectedEntityIds` で受け取る。共有コンテキストへ載せると、1 回の選択変更で全 Entity が再描画される。各 Entity の選択状態は、ストアの Entity ごとの値で判定する。
- シーンから導出してコンテキストや依存配列へ渡す値は、内容が変わらない限り前回のオブジェクト参照を返す。主光源は `useContentStable`、スクリプトの実行順は `useStableMap` を通している（`content-equal.ts`）。導出値をそのまま全 Mesh が参照するコンテキストへ渡すと、1 つの Entity を動かしただけで全 Mesh が再描画される。
- Entity の描画コンポーネントへ渡すアセットマニフェストには、`tracked-assets.ts` の `useTrackedAssets` が返す参照を使う。この参照は Entity ごとに読み取ったアセットを記録し、関係するアセットが変わったときだけ新しいオブジェクトになる。マニフェストをそのまま渡すと、1 つのマテリアルを編集するたびに無関係な Entity まで再描画される。この参照は読み取り専用とし、書き込み、元マニフェストとの同一性比較、`postMessage`、`structuredClone` には使わず、保存や編集には元のマニフェストを渡す。
- `VisualEditorPrototype` から各パネルへ props を渡すときは、`stable-panel.tsx` の `withStableHandlers` を通す。名前が `on` で始まる関数はイベントや effect から呼ぶハンドラとして扱い、関数参照を変えずに最新の処理を呼び出す。描画中に呼ぶ関数には `on` 以外の名前を付け、`useCallback` で参照を固定する。props へ渡す JSX は `useMemo` で保持する。小さなオブジェクトや配列は内容比較されるため、再レンダリングごとに作り直してよい。
- effect から state を空の値へ戻すときは、モジュール内の共通定数を渡す。`setTextures({})` のように新しい空オブジェクトを渡すと、内容が同じでも再描画が 1 回増える。Mesh ごとのフックであれば、アセット編集のたびに全 Mesh が 2 回描画されることになる。
- 一覧パネルの行数が Entity 数やアセット数に比例する場合は、行コンポーネントを `memo` で分離する。行から親のクロージャを呼ぶ場合は、再レンダリングごとに更新する 1 つの ref にまとめて渡す。クロージャを直接 props に渡すと毎回参照が変わり、`memo` が効かない。
- Scene View の描画品質には、CSS 表示サイズに対する固定の割合を使う。React Three Fiber に `devicePixelRatio` の範囲を渡すとディスプレイの倍率をその範囲に丸める挙動になり、1 倍のディスプレイでは描画ピクセル数を減らせない。ラベルに示す割合と実際の描画ピクセル数を一致させる。

## ChatGPT と手動編集を続ける

制作チャットには Pi Coding Agent SDK を使う。`packages/studio-pi` がモデルとツールのループを担い、Studio の正式な編集・検証・保存・撮影ツールを呼び出す。正式ツールを直接登録し、Pi 標準の `tool_search` と `codemode` で探索と操作を組み立てる。固定した担当別セッション、Studio 独自のターン数・実行回数・制作時間の予算、旧 JSON 一括生成、独自の再計画ループは追加しない。

作品・シーン・`generationId` を固定し、リビジョン競合は正式ツールのエラーとして Pi へ返す。停止後の新しい操作は拒否し、すでに渡したエディター処理の完了を待ってから実行枠を解放する。保存済みの部分成果と手動編集はそのまま残す。

保存、Project Health、実際の描画画像が現在のフィンガープリントと一致し、完成条件を満たしたときだけ完了にする。変更がない操作は保存件数に数えない。Plan は読み取り専用とし、確認後にシーンが変わった場合は再作成を求める。詳細と試験範囲は [Pi SDK による Studio 制作](./CHATGPT_AUTHORING.md) を参照する。

通常の制作に管理役のセッションや工程ごとの承認を挟まない。重要な判断だけをユーザーへ返し、編集後に質問するときは現在のシーンを明示的に保存してから行う。回答では元の依頼元・編集先、保存件数、使用量、Revert 用の控えを引き継ぐ。コンテキスト圧縮は Pi に任せ、圧縮後は標準の `context` フックで現在の依頼・条件・回答を添える。

入力キューは引き続き作品・シーン・チャットごとに管理する。各依頼のモデル、思考量、制作方法、添付を保持し、送信直前のシーンに対して実行する。停止・失敗・Plan 確認待ちの状態では、次の依頼を自動で開始しない。

## MCP とネイティブの契約

- AI クライアントは MCP ツールの `description` とサーバーの `instructions` を操作説明として参照する。ツールを追加・修正するときは、機能、選ぶ基準、実行後の操作、失敗しやすい条件を明記し、代替ツールがあれば名前も挙げる。説明だけでは防げない失敗には、戻り値の `harness` 警告など実装側の対策も用意する。
- Rust コマンドへ外部入力を渡すときは、既存のパス検証と権限制御を維持し、任意のパス実行や削除を追加しない。
- 外部ストアの配布元が使う正規 CDN へのリダイレクトを、別サイトからのダウンロードとして誤って拒否しない。ダウンロードの入口と各リダイレクト先は、送信前に配布元ごとの HTTPS・ホスト・配布パスで検査する。たとえば ambientCG は `ambientcg.com/get` から `acg-download.struffelproductions.com/file/ambientCG-Web/download/` へリダイレクトする。全ホスト許可や、最終 URL だけの事後検査で対処しない。
- ストアから取り込むモデル形式は、配布元のファイル情報にある glTF・GLB だけを選ぶ。
  - 自己完結した GLB は元のバイト列を変換せずに保存し、署名、バージョン、コンテナ長、外部参照、保存先、通常ファイルの検査を維持する。
  - GLB にはストア・取り込み共通の固定バイト上限を適用しない。ブラウザ版ストアでは先頭の GLB 署名と宣言サイズを検査して読み取り、保存時のファイル・トランザクション上限も正規 GLB に限り対象外とする。
  - 配布情報のサイズ・ハッシュとライセンス情報を保持し、再読み込みにも同じ元バイト列を使う。ZIP 展開や画像・音声などの既存保護は別に維持する。
  - メモリー確保や保存領域不足のエラーは、形式・配布先の拒否と区別して報告する。

## IPC・CLI 連携

Tauri コマンドを追加するときは、`src-tauri/src/lib.rs` の `#[tauri::command]` と `generate_handler!` への登録、`src/lib/tauri.ts` の型付きラッパーを揃える。Rust 側の snake_case と `invoke` 側の camelCase の引数対応を確認し、必要な権限だけを `src-tauri/capabilities/default.json` に追加する。

CLI 連携は `src/lib/xrift-cli.ts` の既存経路を使い、`LogLine` でログを流す。処理中の busy / finally 管理と二重操作防止には既存の `wrap` パターンを使う。依存パッケージを追加する場合は必要性を説明し、ロックファイルを更新する。フロントエンドと Rust の変更に応じた検証手順は [開発ガイド](../DEVELOPMENT.md) を参照する。

Rust からバックグラウンドの外部プロセスを起動するときは、`background_process::command` または `background_process::tokio_command` を使う。Windows では `CREATE_NO_WINDOW` によって別コンソールウィンドウを開かず、進捗と診断出力を既存のパイプ・ログ・チャットへ流す。制作チャットの Node.js、CLI、Blender、Git、FFmpeg、停止コマンドにも同じ起動処理を適用する。ユーザーが明示的に開くアプリやブラウザには既存の opener を使う。
