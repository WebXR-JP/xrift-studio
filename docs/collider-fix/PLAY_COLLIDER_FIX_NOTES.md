# 最終版: Collider 設定と Play 実行時の修正

対象: `xrift-studio-collider-fix.zip` をもとにしたソース一式。前回の Collider 設定・形状生成の修正をすべて引き継ぎ、Play 実行経路の修正を追加しています。

配布物は修正済みソースの ZIP であり、ビルド済みの Windows アプリではありません。アプリ全体のビルドや画面上での Play 操作は、この環境では確認できていません。

## Play 側で追加修正した問題

### 1. Physics の初期化前に「準備完了」になる

Play の外側にある読み込み監視では、Physics や Suspense の配下がまだマウントされていない段階でも、読み込み中のモデル数が 0 件と判定されることがありました。初期化が遅れると、モデルがまだ登録されていないだけなのに準備完了になってしまう経路です。

`SceneModelLoadCommit` を実際の Physics 配下に配置し、シーンがコミットされるまで準備完了にしないようにしました。非同期モデルと衝突用モデルは、最初の通知を待たずレイアウトエフェクト（`useLayoutEffect`）で読み込み中として登録します。

### 2. モデルの読み込み完了と衝突形状の登録完了が別

モデルの読み込み完了だけで歩行を開始せず、Mesh Collider から実際の Rapier Collider 参照を受け取り、物理空間に登録されたことまで確認するようにしました。形状更新ごとに世代を分け、古い生成結果が新しい形状の準備完了を通知しないようにしています。

準備中は重力だけでなく Physics 自体を一時停止します。準備完了後に物理計算を 1 ステップ進め、その通知を受けてから既存の公式 `PhysicsPlayer` をマウントします。プレイヤー制御を独自実装に置き換えたわけではありません。

### 3. 失敗した読み込みを成功扱いしない

モデルの読み込み失敗、衝突用モデルの欠損、指定した共有ノードに有効な衝突形状がない場合などは、開始前のエラーとして扱います。準備完了にはせず、既存の Play 表示に原因と停止後の確認案内を出します。失敗を仮の箱や仮の床で隠すことはしません。

複数のメッシュの一部に無効な面があっても、有効な形状を取得できる部分はそのまま使います。候補があるにもかかわらずすべて無効な場合は生成エラーにします。子がまだないコンテナ自体は不正なモデルとして扱いません。

### 4. Stop → Play の古い状態を持ち越さない

編集と Play の切り替えごとに、Physics と読み込みトラッカーを作り直します。停止済みの読み込み通知・タイマー・形状更新の結果は破棄し、前回の準備完了状態を次の Play に再利用しないようにしました。

### 5. 共有モデルの一部を Collider にした場合

`sourceNodeIndex` も読み込みの依存関係に含めました。別ノードに切り替えた直後に、前のノードの衝突形状が使われてしまうのを防ぎます。また、指定された衝突用モデルが欠けているときに、利用者に知らせず描画用モデルで代用する経路も取り除きました。

### 6. ランタイムと出力側

Play・ランタイム・Classic JSX 出力で、共通のメッシュ衝突生成ソースを使います。追加した型・Context・Hook の依存関係も Classic JSX に含め、生成される補助コードの構文を検査しています。

ランタイムの非同期ロード前後で Hook の呼び出し数が変わる経路も修正しました。

## 未確認・反映が必要な範囲

この環境では依存パッケージを取得できず、アプリ全体の型チェックは React・Three.js・Rapier などの未導入エラーで失敗しました。プロジェクト指定の TypeScript 7.0.2 ではなく、環境内の 5.8.3 による限定的な検証です。依存定義とロックファイルは変更していません。

アプリ全体のビルド、コンパイラーの全フィクスチャ、ブラウザや Tauri の実際の画面での Play、公開先の動作確認は未実施です。単体テストの成功をもって実際の画面での不具合解消が確認済みとは見なしていません。

`public/xrift-runtime-shell` は元の事前ビルド済みファイルをそのまま残しています。ソース修正は含まれていますが、ブラウザから直接公開するシェルに反映するには、依存導入後に再ビルドが必要です。エディター本体の Play は今回修正したソース側の経路を使います。

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm cli:test
pnpm runtime:build
node scripts/build-world-runtime-shell.mjs
pnpm build
```

上記は実際の開発環境で行う手順であり、この ZIP を作成した環境ですべて実行・成功したコマンドではありません。生成済みシェルの文字列を手動で書き換えたり、再ビルド済みとしてマニフェストを偽装したりはしていません。

## 実際の画面での確認手順

1. 修正済みエディターを起動して既存プロジェクトを開きます。Play 中であれば一度停止します。
2. 対象メッシュで「当たり判定に追加」を実行します。既存の Mesh Collider を手動で削除して作り直す必要はありません。
3. Play を開始し、準備表示が消えてから床に着地すること、壁をすり抜けないことを確認します。
4. Stop →「当たり判定から外す」→ Play の順に操作し、対象の判定がなくなっていることを確認します。
5. 「これだけを歩けるようにする」、共有モデルの別ノード、既存 Mesh Collider の再有効化、Stop → Play の繰り返しについても確認します。

開始待ちは初回スポーン用の仕組みです。Play 開始後の追加ストリーミングでプレイヤーを毎回再生成する設計にはしていません。また、Shader や Skinned Mesh の毎フレーム変形に追従する判定や、公式ギミック内部が独自に生成する Collider の一括解除は対象外です。
