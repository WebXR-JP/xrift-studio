# XRift Studio UX 原則

XRift Studioでは、利用者が制作を続けやすい画面を設計する。現在の状態、次にできる操作、操作後の結果を分かりやすく示す。

機能の追加、既存画面の変更、画面文言、レビューでは、この文書を共通の判断基準にする。実装時は`AGENT.md`のルールと`.agents/skills/xrift-studio-ux/SKILL.md`の手順も参照する。

状態ごとの動きと機能一覧は [マイクロインタラクションWiki](./UX_INTERACTIONS.md) に従う。新機能の実装時は、その機能IDと参照する`MI-xx`を明記する。右設定の密度、枠、参照フィールドは [設定デザインガイド](./EDITOR_INSPECTOR_DESIGN.md) に従う。

## 操作と結果の表示方針

### 1. 必要な変化を、必要な時に、行動できる形で届ける

更新が必要になったら、現在の状態と最新版の違いを画面に示す。同じ場所から更新できるようにし、後回しにする操作も用意する。処理中と完了後の状態を区別して表示する。

画面表示を妨げないタイミングで状態を確認し、変更が必要なときに理由と差分を提示する。主操作は一つに絞り、延期や閉じる操作も安全に行えるようにする。実行中は重複操作を防ぎ、成功後は状態を再取得して表示を更新する。

現行実装では、`App.tsx`が起動後にCLIの現在・最新バージョンを確認する。`UpdateDialog.tsx`が差分、更新、後で行う選択をまとめて提示する。

### 2. 完了を次の開始点にする

作成、起動、公開の成功後は、結果を開くか、一操作で開ける表示を残す。作成直後なら新しいワールドやアイテム、実行後なら起動URL、公開後なら公開先が対象になる。

成功時は結果のID・URL・パスを確定し、成果物を選択するか、結果を開く操作を表示する。成功トーストに加え、結果へ移動できる表示を必ず残す。失敗時も編集中の対象や入力を保持し、ログ、再試行、編集画面などの復帰手段を示す。

現行実装では、作成完了後にプロジェクト一覧を再取得し、新しいプロジェクトを選択する。エディターでは実行中のローカルURLと公開済みURLをその場で開ける。

### 3. 公開前に、初期状態を作り手の表現へ置き換える

テンプレートから作ったワールドやアイテムを、そのまま公開すると他の作品と見分けにくい。アップロード直前に`xrift.json`のタイトル・説明とサムネイルを確認する。テンプレートの値や画像が残っていたら、公開を開始せず編集画面へ案内する。保存後に未完了の項目を再確認し、すべて整ったらアップロードを続ける。

公開前の確認と編集を同じ操作の流れに組み込み、初期ワールドのままに見える作品を公開するのを防ぐ。初期値の判定条件は、CLIのテンプレート変更に合わせて見直す。

### 4. 一覧を制作の記憶と入口にする

プロジェクトライブラリでは、利用者が作品を選んで制作を再開できるようにする。各カードはサムネイル、名前、タイトル、説明で見分けられるようにし、新規作成の入口は常に一覧の先頭に置く。件数、保存場所、作品がない状態も表示する。

新規作成は作品がない場合も操作できるようにする。各項目には見た目の手掛かりと識別に必要な情報を載せる。読み込み中、作品なし、失敗、更新後は表示を分ける。一覧から作品を開く、サムネイルを変更する、公開先を確認する操作は、対象の近くに置く。

現行実装では、`ProjectLibrary.tsx`が先頭の新規プロジェクトカード、件数、空状態、グリッドを管理する。`ProjectCard.tsx`には種別、サムネイル、名前を目立つ位置に表示する。

### 5. 状態を隠さず、静かに変化を伝える

操作結果だけでなく、いま何が起きているかも示す必要がある。処理中のラベル、無効化、起動中のURL、成功・失敗の通知を一貫して使う。視覚表現は落ち着いた基調を保つ。色と動きは意味を補強するためにだけ使う。

- 白とニュートラルカラーを基調にする。ブランド色は主操作と注目すべき結果に限定する。
- 通常、ホバー、無効、実行中、成功、失敗を視覚と文言の両方で区別する。
- 短いフェードや移動は、表示されたことや画面が切り替わったことを示す範囲に留める。
- 主要操作はアイコンだけにせず、読める操作名を添える。Markdown文書と画面文言には絵文字を使わない。

### 6. 既存の画面言語を継承する

新しい画面は、同じ画面にある既存のモーダル、ダイアログ、ボタン、通知を視覚的な基準にする。`gradient-brand-soft`、白・zinc基調、`brand`色の主操作、既存の角丸・余白・フォーカス表現など、既に使われているトークンと構造を優先する。新しい色スケールや強い装飾を追加しない。意図的に既存パターンから外れる場合は、対象状態と理由を機能仕様へ残す。

## 新機能の設計手順

1. 利用者が何をできるようになるかを一文で書く。実装内部の操作だけを目的にしない。
2. 操作前、処理中、成功、失敗、一覧や前画面への復帰の五つの状態を書き出す。
3. 各状態で画面が示す事実、主操作、戻る先を決める。主操作は一つに絞る。
4. 成功時に次の目的地を開くか、目的地をすぐ開ける状態を残す。
5. 既存のライブラリ、エディター、更新ダイアログのどこに戻るかを決める。一覧の情報も更新する。
6. 実装後に実画面で確認する。操作名だけで次の一手が分かるかを検証する。

## レビュー用チェックリスト

- [ ] 画面を開いた直後に、対象の状態と主操作が分かる。
- [ ] 作成・起動・公開・更新の成功後に、結果そのものへ到達できる。
- [ ] アップロード前にタイトル、説明、サムネイルがテンプレートのままではないことを確認する。未完了なら編集から公開へ戻れる。
- [ ] 実行中の表示、二重操作の防止、安全な中断の可否が一致している。
- [ ] 失敗時に原因を確認する場所または再試行の方法がある。
- [ ] 一覧には新規作成の入口、項目を見分ける情報、空状態の次の一手がある。
- [ ] 色、動き、アイコンで状態や操作の意味を分かりやすく示している。
- [ ] 既存画面のコンポーネントと色・余白・角丸・フォーカス表現を比較する。独自の見た目を増やしていない。
- [ ] 画面文言とMarkdown文書に絵文字がなく、主要操作を言葉で理解できる。

## 避けること

- 成功トーストだけを出して、成果物やURLへの導線を残さない。
- 更新の必要性や差分を示さず、更新を強いる。
- 一覧を空白にし、新規作成や再開の入口を失わせる。
- 実行中なのに通常時と同じ操作を可能にし、二重実行や安全でない閉じ方を招く。
- ブランド色、強い影、動きを常用する。どれが重要な状態か分からない表示になる。
- アイコンや絵文字だけに操作や状態の意味を持たせる。


## 編集導線の判断基準

新規配置は「素材を追加」とHierarchyの空白部分の右クリックから行えるようにする。既存Entityの設定はInspector、選択対象の編集はScene / Hierarchyの共通右クリックメニュー、保存・全体書き出し・公開は既存のヘッダーに置く。

一つの操作に複数の入力手段がある場合も、command・ラベル・無効理由を共用する。タッチとキーボードでも同じ操作に到達できることを確かめる。

UI変更の受け入れ確認は「作成 → 配置 → 設定 → Play → 保存」「選択範囲を書き出す → 別World/Itemへ追加 → Undo/Redo」「参照切れを確認 → 対象へ移動 → 設定を直す」の作業単位で行う。所要時間やクリック数を収集する仕組みは今回作らない。操作前・処理中・失敗・復帰先をコードと試験で確認し、実機で未確認なら記録を分ける。
