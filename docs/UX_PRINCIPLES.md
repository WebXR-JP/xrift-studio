# XRift Studio UX 原則

XRift Studio では、ユーザーが迷わず制作を続けられる画面を設計する。現在の状態、次にできる操作、操作後の結果を分かりやすく伝えることを基本とする。

機能の追加、既存画面の変更、画面文言の検討、レビューでは、この文書を共通の判断基準とする。実装時は `AGENT.md` と `docs/UX_INTERACTIONS.md` もあわせて参照する。

状態ごとの動きと機能一覧は [機能別の操作・状態設計](./UX_INTERACTIONS.md) に従う。新機能の実装時は、該当する機能 ID と参照する `MI-xx` を明記する。右側の設定パネルの密度、枠、参照フィールドは [設定デザインガイド](./EDITOR_INSPECTOR_DESIGN.md) に従う。

## 操作と結果の表示方針

### 1. 必要な更新を適切なタイミングで示し、その場で対応できるようにする

更新が必要になったときは、現在の状態と最新版の違いを画面に示す。同じ場所から更新を実行できるようにし、後回しにする選択肢も用意する。処理中と完了後の状態は明確に区別して表示する。

画面操作を妨げないタイミングで状態を確認し、変更が必要な場合に理由と差分を提示する。主操作は 1 つに絞り、延期や閉じる操作も安全に行えるようにする。実行中は二重操作を防ぎ、成功後は状態を再取得して表示を更新する。

現行実装では、`App.tsx` が起動後に CLI の現在バージョンと最新バージョンを確認し、`UpdateDialog.tsx` が差分・更新・後で行う選択をまとめて提示する。

### 2. 完了画面から次の行動へつなぐ

作成・起動・公開が成功したあとは、結果をそのまま開くか、1 回の操作で開ける導線を残す。作成直後なら新しいワールドやアイテム、起動後ならローカル URL、公開後なら公開先が対象になる。

成功時は結果の ID・URL・パスを確定させ、成果物を選択するか、結果を開く操作を表示する。成功トーストだけでなく、結果へ移動できる表示を画面に残す。失敗時も編集中の対象や入力内容を保持し、ログ、再試行、編集画面などの復帰手段を示す。

現行実装では、作成完了後にプロジェクト一覧を再取得して新しいプロジェクトを選択する。エディターでは実行中のローカル URL と公開済み URL をその場で開ける。

### 3. 公開前にテンプレートのままの情報を確認する

テンプレートから作ったワールドやアイテムを初期値のまま公開すると、他の作品と見分けがつかない。アップロード直前に `xrift.json` のタイトル・説明・サムネイルを確認し、テンプレートの値や画像が残っていれば公開を開始せず編集画面へ案内する。保存後に未完了の項目を再確認し、すべて整った段階でアップロードへ進める。

公開前の確認と編集を同じ操作の流れに組み込むことで、初期状態のまま作品が公開されるのを防ぐ。初期値の判定条件は、CLI のテンプレート変更に合わせて見直す。

### 4. 一覧からすぐ制作を再開できるようにする

プロジェクトライブラリは、ユーザーが作品を選んで制作を再開するための入口とする。各カードにはサムネイル、名前、タイトル、説明など見分けるための情報を載せ、新規作成の入口は常に一覧の先頭に置く。件数、保存場所、作品が 0 件の状態も分かりやすく表示する。

作品がない状態でも新規作成をすぐ操作できるようにする。読み込み中、作品なし、取得失敗、更新後の各状態は表示を分ける。一覧から作品を開く、サムネイルを変更する、公開先を確認するといった操作は対象の近くに配置する。

現行実装では、`ProjectLibrary.tsx` が先頭の新規プロジェクトカード、件数、空状態、グリッド表示を管理し、`ProjectCard.tsx` が種別、サムネイル、名前を目立つ位置に表示する。

### 5. 状態を隠さず、控えめな表現で変化を伝える

操作の結果だけでなく、いま何が起きているかも画面上で分かるようにする。処理中ラベル、操作の無効化、起動中 URL、成功・失敗の通知を一貫して使う。全体の視覚表現は落ち着いたトーンでまとめ、色と動きは意味を補強するためにだけ使う。

- 白とニュートラルカラーを基調にし、ブランド色は主操作と注目すべき結果に限定する。
- 通常、ホバー、無効、実行中、成功、失敗を、見た目と文言の両方で区別する。
- 短いフェードや移動は、要素の表示や画面の切り替わりを伝える範囲にとどめる。
- 主要操作はアイコンだけにせず、読める操作名を添える。Markdown 文書と画面文言に絵文字は使わない。

### 6. 既存画面のデザインルールを引き継ぐ

新しい画面は、同じ画面にある既存のモーダル、ダイアログ、ボタン、通知を視覚的な基準とする。`gradient-brand-soft`、白・zinc 基調、`brand` 色の主操作、既存の角丸・余白・フォーカス表現など、既に使われているトークンと構造を優先して再利用する。新しい色スケールや強い装飾は追加しない。意図的に既存パターンから外れる場合は、対象の状態と理由を機能仕様に残す。

## 新機能の設計手順

1. ユーザーが何をできるようになるかを 1 文で書く。実装内部の処理だけを目的にしない。
2. 操作前、処理中、成功、失敗、一覧や前画面への復帰という 5 つの状態を書き出す。
3. 各状態で画面に示す事実、主操作、戻る先を決める。主操作は 1 つに絞る。
4. 成功時に次の目的地を開くか、すぐ開ける状態を残す。
5. 既存のライブラリ、エディター、更新ダイアログのどこへ戻るかを決め、一覧の情報も更新する。
6. 実装後に実際の画面で確認し、操作名だけで次の一手が分かるか検証する。

## レビュー用チェックリスト

- [ ] 画面を開いた直後に、現在の状態と主操作が分かる。
- [ ] 作成・起動・公開・更新の成功後に、結果そのものへ到達できる。
- [ ] アップロード前にタイトル・説明・サムネイルがテンプレートのままではないことを確認し、未完了なら編集から公開へ戻れる。
- [ ] 実行中表示、二重操作の防止、安全な中断の可否が一致している。
- [ ] 失敗時に原因を確認する場所または再試行の手段がある。
- [ ] 一覧に新規作成の入口、項目を見分ける情報、空状態の次の一手がある。
- [ ] 色、動き、アイコンで状態や操作の意味が分かりやすく伝わる。
- [ ] 既存画面のコンポーネントと色・余白・角丸・フォーカス表現を比較し、独自の見た目を増やしていない。
- [ ] 画面文言と Markdown 文書に絵文字がなく、主要操作を言葉だけで理解できる。

## 避けること

- 成功トーストだけを出して、成果物や URL への導線を残さない。
- 更新の必要性や差分を示さず、更新を強制する。
- 一覧を空白のままにし、新規作成や制作再開の入口を失わせる。
- 実行中なのに通常時と同じ操作を許可し、二重実行や安全でない中断を招く。
- ブランド色、強い影、動きを常用して、重要な状態が埋もれるようにする。
- アイコンや絵文字だけに操作や状態の意味を持たせる。

## 編集導線の判断基準

新規配置は「素材を追加」と Hierarchy の空白部分の右クリックから行えるようにする。既存 Entity の設定は Inspector、選択対象の編集は Scene / Hierarchy 共通の右クリックメニュー、保存・全体書き出し・公開は既存のヘッダーに配置する。

1 つの操作に複数の入力手段がある場合でも、コマンド・ラベル・無効時の理由を共通化する。タッチ操作とキーボード操作のどちらでも同じ操作へ到達できることを確認する。

UI 変更の受け入れ確認は、次の作業単位で行う。

- 作成 → 配置 → 設定 → Play → 保存
- 選択範囲を書き出す → 別のワールド / アイテムへ追加 → Undo / Redo
- 参照切れを確認 → 対象へ移動 → 設定を修正

所要時間やクリック数を収集する仕組みは設けない。操作前・処理中・失敗・復帰先をコードとテストで確認し、実機で未確認の項目があれば記録を分けて残す。
