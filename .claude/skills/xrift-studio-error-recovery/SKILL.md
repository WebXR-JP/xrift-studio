# エラーの再現と修正

ログを読み、最小構成で問題を再現してから、生成処理の原因を修正してください。利用者の作品は保ちます。個人のパス、ワールドID、トークン、画像はテストや文書へ転記しません。報告では、原因、修正、検証した結果を読み取りやすい日本語で伝えてください。

## 公開エラーを調べる場所

| 調べる処理 | ソース |
|---|---|
| 保存、コンパイル、ステージング、CLI検査、送信 | `src/lib/visual-editor/publish.ts` |
| 機能ごとの公開用ファイルの選択 | `src/lib/visual-editor/compiler/compile.ts` |
| runtimeの同梱、importの書き換え | `script-emit.ts`、`scene-postprocessing-emit.ts` |
| Playと公開コードの共通処理 | `packages/xrift-studio-runtime/src/` |
| 公開テンプレートと同じ条件での生成コードの型チェック | `cli/convert.fixture.mjs`の`runStagedWorldTypecheck`、`typecheckWithTemplateOptions` |

生成コードで`Cannot find module`が出たら、参照ファイルの同梱漏れと、平坦化後の相対importを調べてください。型だけのimportも、公開前のtscで必要です。後続のimplicit anyは、型の欠落から生じているか確認します。anyの追加や型チェックの無効化でエラーを回避しません。

## 再発を減らす修正

一時的なステージングファイルに加えて、生成元を修正してください。原因が分からないまま、利用者のScene、Script、Assetを削除・初期化しません。

見た目に差がある場合は[描画の契約](../../../docs/AGENT_IMPLEMENTATION.md#rendering-parity)に従います。同じ素材、ローダー、シェーダー、描画処理を使うように修正してください。公開側だけの代替材質や色補正は加えません。画像の自動変換や公開前の警告だけで対処を終えず、作者が見ている素材を公開時にも使う処理を修正します。

多数の機能を含むテストでは、別の機能が必要なファイルを同梱し、欠落を見逃す場合があります。失敗した機能の最小構成と、依存ファイルを補っていた機能を含まない構成を検査してください。例として、Scriptなしのポストエフェクトや、Text・Image本体なしの制御処理があります。報告に合う構成を選び、無関係な組み合わせは増やしません。

アプリ本体の型チェックに加え、問題が発生した生成物も検証します。可能なら、修正前に同じエラーが発生し、修正後に解消することを確かめてください。一時プロジェクトを使い、検証のために実ワールドや公開先を変更しません。検証手段はxrift-studio-verifyから選びます。

再試行に問題がある場合は、設定への記録と処理の完了を分けて確認してください。package.jsonに依存を記載しただけでは、取得は完了していません。繰り返し書き出すテストでは、元コードのバックアップと、途中で加えた変更も残ることを確認します。

報告には原因、修正内容、検証範囲、未検証の内容を記載してください。コードの修正、配布、再公開は、それぞれの実施状況を示します。

## SDKの難読化検査が依存ライブラリを拒否した場合

`no-obfuscation`で指摘された変数を、生成したchunkから依存パッケージの配布コードまでたどってください。`target: 'esnext'`と`minify: false`でも、配布済みコードの補助関数名は残ります。three-vrmの`__defNormalProp`と`__getOwnPropSymbols`は、この処理で誤判定されます。

three-vrmの同梱コードは、`node scripts/prepare-readable-three-vrm.mjs --check`で固定バージョンの原本と比較します。更新時は同じスクリプトで再生成し、元のライセンスを保ってください。拒否された既知のprivate bindingだけを、構文解析で改名します。文字列、プロパティ名、公開export、利用者のコードは書き換えません。

クラスの内部名を変える場合は、元のconstructor.nameとdescriptorを保ってください。定義中に名前を読む処理など、原本の構造が変わっていたら生成を止めて見直します。検査ルールは無効化しません。

型チェック後に、隔離した生成物を実際にビルドし、公式CLIで検査してください。変更前の拒否理由と変更後の結果を記録し、同じ素材で編集画面と生成コードの描画も比較します。

## スキルの改善

新しい報告から、ほかの修正でも使える判断が得られた場合は、該当する手順を更新してください。個別ログの蓄積や、全作業に適用する禁止事項の追加は避けます。変更後は`.agents/skills/`と`.claude/skills/`のコピーを同期します。
