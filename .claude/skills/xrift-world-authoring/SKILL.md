# XRift Studio でワールドと 3D モデルを制作する

最初に `list_projects` と現在の Scene を確認する。接続中の Studio からは `get_world_authoring_guide` で最新の制作ガイドを取得できる。このスキルには、基本方針と品質改善の手順をまとめている。

## 進め方

1. **作業対象と完成基準を先に決める**。ツールを選ぶ前に、依頼の範囲が一部の修正、モデル1点、周辺を含めた配置、ワールド全体のどれかを判断し、役割と見る距離に応じた密度で作る。近くで見る建物には構造の細部を作り込む一方、街全体では通りや建物の統一感を優先し、すべての建物に内装までは作らない。作者の意図から具体的な完成条件を数件定め、高評価の作例がある場合は「輪郭・質感・動きのどこが良いのか」まで言語化して基準にする。

2. **現在の Scene を確認し、編集対象と既存の制作物を正確に把握する**。修正対象の寸法・向き・名前・Material・動作など、引き継ぐべき特徴を先に控え、元の版・前回版・今回版は名前や撮影画像で対応付けておく。ワールド全体の依頼を、いま選択されている Entity だけの修正に狭めてはいけない。新規ワールドの starterEntityIds は必要に応じて置き換えてよく、初期形状を残すためだけに不要な要素を足さない。依頼範囲外の制作物や作者の手動編集は壊さず残す。

3. **既存の制作物を直すときは、手を入れる前に欠点が出る状況を再現して優先順位を決める**。見た目は想定距離や問題が見える角度から撮影し、動作は不具合が起きる操作で確認する。普段の視点で目立つ破綻（輪郭や比率のずれ、浮いた部品、板で塞がった開口部、引き伸ばされた模様など）、進行を止める不具合、複数対象に共通する問題から優先して直す。ポリゴン数や作業量で品質を判断せず、原因に合う最小の単位を直す（形・UV の貼り方・状態や接続・情報の順序など）。良い形や動きはそのまま残し、詳しい手順は topic: refinement を参照する。

4. **ワールド全体を作るときは、先に空間全体の設計をまとめる**。構図、人の身長に対する比率、動線、主役と周辺要素、配色、背景・照明、空間内の案内を一体で計画し、最初の保存時点で空間として成立する状態に仕上げる。床や小物1点だけではワールド完成とは言えない。展示・教材・メニュー・サインには topic: spatial-ui、背景や環境づくりには topic: environment を参照する。1枚の掲示板に長文を詰め込まず、読みやすいカードと実物の見本で体験を組み立て、作者が意図した簡素さや暗い演出は尊重する。

5. **3D モデルは資料から固有の形と比率を読み取り、形を先に作って表面を後から合わせる**。輪郭・断面・厚み・開口部の奥行き・部品同士の接合・床への接地を先に作り込み、形状の甘さを色や模様だけでごまかさない。家具や建築、主役モデルに単色の箱を置いただけで終えず、必要な曲面や面取りには外部素材や Blender を活用する（教材の見本や作風として意図された単純形状は残す）。近くで輪郭や影に出る部分は形状で、細かな質感や模様は Material と Texture で表現し、詳しい基準は topic: model-quality を参照する。

6. **目指す完成形と使える機能に応じて制作方法を使い分ける**。作品内・外部の素材、建築などに再利用しやすい静的ソース、空間 UI 用の UIKit Script Render、独自形状向けの Blender を適材適所で組み合わせる（Blender は必須ではない）。作者が制作方法を指定した場合はそれに従い、詳細ガイドは実際に使う分だけ読む。外部素材は完成度を高めるうえで不足している用途に絞って探し、カタログの総当たり調査や、繰り返し使う要素の個別生成を前提にしない。

7. **繰り返し使う要素は Prefab 化して再利用し、主役や見える構造に手間を集中させる**。木・ベンチ・街灯のように複数置くものは、1つを仕上げて create_prefab で Prefab にし、ほかは place_asset で配置する（get_editor_context の prefabs に使えるものがあれば流用する）。全配置をまとめて直すときは元 Entity を編集して update_prefab_from_source で反映し、配置ごとの差は位置・向き・大きさで付ける。別バリエーションが複数必要なら別 Prefab に分け、1つだけ個別に変える場合は unpack_prefab_instance で通常の Entity に展開する。隠れる細部は省き、体験に必要な設備と利用スペースを確保してから周囲を飾る。

8. **保存した最終成果物を、同じ条件で比較して完成を判断する**。全体がまとまった状態で保存し、想定距離から実際の描画を確認して完成条件と照らし合わせる。修正した箇所は直す前と同じ視点と照明で撮影して見比べる。動作は直す前後に同じ操作を与えて結果を比べ、隣接する既存操作も1つ確認する。画像で改善点や残課題が判別できなければ視点を変えて撮り直し、問題が残る箇所だけをピンポイントで直す。データ構造や Entity の件数だけで品質や動作を確認済みとみなしてはならない。

9. **既存の配置や動作を壊さず差し替えられる状態で仕上げる**。一部を作り替えるときは、対象 Entity の配置・既存動作・手動で追加された子要素を維持し、ルートや描画を二重にせず見た目だけを置き換える。編集元のデータを残したうえで、維持した点・直した点・確認した条件・残る課題を報告する。基準を満たしたものだけを完成として扱い、未確認の項目とは明確に分ける。

10. **実行上限と完成確認の記録に従って作業を進める**。完成条件を満たしたら終了し、追加の書き込みが許可されない状態になったら、保存済みの結果と具体的な残作業を報告して止める。作者から依頼の変更がない限り、再開時も同じ上限と完成条件を引き継ぐ。未確認の動作はそのまま正直に報告し、公開は明示的に依頼された場合だけ実行する。

11. **作者が継続やルール調整を明示的に許可している場合は、すでに合意した内容について確認を繰り返さない**。現在の保存状態と停止理由を読み取り、ソース変更・非同期処理の完了・同じ失敗の繰り返しを区別したうえで、許可された範囲から続きを進める。過去の停止履歴を消したり、反復失敗を防ぐ制限を無制限に緩めたりしない。

## 既存の制作物の品質を上げる

既存のモデル・動作・案内の品質を、基準版と修正版を同じ条件で比較しながら高める共通手順。症状ごとの確認箇所と着手点、比較方法、複数件の記録方法をまとめている。`get_world_authoring_guide` の `topic: "refinement"` に相当する。

1. **依頼内容と基準版を整理する**。変更する箇所、残す特徴、実際に利用・鑑賞する状況を短く控える。作者が高く評価した作例がある場合は「輪郭・質感・動きのどれが良いのか」まで言葉にしておく。元の版・前回版・今回版は Asset 名・revision・撮影画像で紐付け、元の版を取得できないときは手元にある基準版と出所を明記する。比較用の一時的な位置・倍率調整と、制作物そのものの変更は明確に分ける。

2. **欠点が出る状況を再現し、症状ごとに確認箇所と着手点を絞る**。口や窓が板に見えるなら正面斜め・開口部の拡大・動きの途中を確認し、上下の縁・奥行き・周囲との接合から直す。模様が帯や渦に伸びるなら側面だけでなく上面・正面・付け根を見て UV と投影から直す。操作中に表示や状態が巻き戻るなら、応答が遅れる状況で操作を素早く切り替えて再現し、状態更新の経路と結果・入力の対応付けから直す。案内で目当ての情報にたどり着けないならスポーン視点から実際に歩いて確認し、入口・情報の順序・操作名から見直す。

3. **修正の優先順位を決める**。普段の視点や操作で目立つ欠点、進行を止める不具合、複数の対象に共通する問題を先に直す。ポリゴン数やコード行数、見た目の派手さだけで重要度を決めない。

4. **原因に合った最小の単位から直す**。形状の問題なら形、模様の歪みなら UV や投影、動作の食い違いなら状態や接続、案内の分かりにくさなら情報設計を直接修正し、表面だけの取り繕いを避ける。問題のない形状・既存動作・呼び出し名・動線はそのまま活かす。資料は実物の写真・設計図・既存仕様を優先し、生成画像は推定を含む補助資料として扱う。

5. **最終成果物を同じ条件で前後比較する**。見た目は元の版・前回版・今回版を同じ照明・角度・画面上の大きさで撮影し、全体と問題箇所の拡大を見比べる（動くモデルは修正部位が変形する姿勢も確認する）。動作は同じ操作手順を Play で実行して結果を比べ、Interactivity グラフは simulate_interactivity_asset で実行経過を比較する。不具合の出た操作に加えて隣接する既存操作も1つ確かめ、非同期処理は到着順、保存処理は保存後に開き直した状態まで検証する。案内は同じ視点・距離で初見の導線と読みやすさ、操作結果を確認し、Play を使えない環境では未確認の動作を明記する。

6. **症状が残る場合は、比較で見えた原因箇所をやり直す**。基準を満たしたものだけを完成とし、未取得・未確認・残る欠点ははっきり区別して引き継ぐ。処理した件数だけで完了と判断せず、制作しただけの未確認物を合格品と混同しない。

7. **独立した対象を並行して進める場合は、担当範囲と保存先を明確に分ける**。着手前に比較条件と完成基準だけを共有し、資料収集・原因調査・独立した修正は同時並行で進めてよい。ただし、Scene への統合・保存・公開は必ず1か所でまとめて行う。

8. **次の作業へそのまま引き継げる形で結果を残す**。維持した点・修正した点・確認条件を記録し、比較対象には版の名前を付ける。複数対象を直した場合は、対象ごとに「対象と版・主な欠点・維持した要素・修正内容・確認の根拠・残る課題」を一覧にし、「保留」には資料不足や未確認の理由を添える。公開・共有・既存ファイルの差し替えは依頼範囲内にとどめ、公開した場合は返された公開先と対象が一致しているか照合する。

## 3D モデルを作る・直す

参考資料と実際の描画結果を見比べ、輪郭・接合・質感・動きの破綻が大きい箇所から直す手順。主役モデルの制作、既存モデルの作り直し、複数モデルの改修を対象とする（配置や照明だけの調整は含まない）。`get_world_authoring_guide` の `topic: "model-quality"` に相当する。

1. **対象モデルと完成基準を明確にする**。制作手段は各ルート（r3f・assets・blender）に従い、ここでは基準・優先順位・確認方法を扱う。対象の Model、使用する Entity、想定される視認距離を特定し、get_model_asset で寸法・マテリアルスロット・アニメーション・編集元の有無を、get_entity_bounds で配置後の実寸を確認する。承認済みや高評価の作例があれば、輪郭・質感・動きのどこが良いのかを言語化して基準にする。元の寸法・向き・名前、Material と Texture、必要なアニメーション名、建築なら階数や開口部・動線など維持すべき特徴を控え、元の版・前回版・今回版を対応付けておく。モデル自体の改修と Scene の配置・照明調整は分けて扱い、依頼範囲を守る。

2. **複数モデルを扱う場合は、最初に各モデルの方針を振り分ける**。「そのまま残す」「既存の良い版を使う」「優先して直す」「保留」のいずれかに分類して記録し、複数モデルに共通する欠点から着手する（記録項目は topic: refinement に従う）。同名の別版は Model ID や出典で区別し、資料や素材が揃わないものは状態を記録して他を先に進める。並行作業するときは対象 Model と保存先を分け、同じ Model を同時に編集しない。

3. **実際の描画を確認し、目立つ破綻から直す順番を決める**。set_scene_view_camera の focusEntityId で対象を画面に収め、正面斜め・背面・上面・接合部の拡大など複数の角度から capture_scene_view で撮影する（側面1枚だけで判断しない）。口や窓は正面寄り、平たいヒレや屋根は上面、膜や薄い板は表裏、ボーン周辺の境目は動作途中など、症状に合う視点を選ぶ。通常の視認距離で目立つ大きな欠点（資料との輪郭のずれ、浮いた部品、板で塞がった開口部、帯や渦に伸びた模様、動くと開く継ぎ目など）を優先する。ポリゴン数やファイル容量だけで判断せず、形が崩れている部位だけを作り直し、形や動きが良いモデルは UV・Material・接合部だけの修正も検討する。

4. **形と比率は信頼できる資料から読み取る**。生物は実物の写真や標本、建物は現地写真・立面図・平面図・寸法を基準とし、作者から提示された参考資料があればそれを最優先にする。画像生成が使える環境では不足する角度や質感の補助資料を作れるが、生成画像だけで種別・構造・寸法を断定せず、推定した箇所は報告に明記する。

5. **形状を先に作り込み、表面の質感は後から合わせる**。輪郭・断面・開口部の奥行き・部品の取り合いを先に整え、基本形状は当たり付けにとどめて形の甘さを色で隠さない。たとえば魚の口なら上下の顎と口内の奥行き、家の窓なら壁の厚み・窓枠の納まり・ガラス面の位置まで造形する。近くで輪郭や影に出る細部は形状で作り、肌・塗装・木目などの細かな表情は Material と Texture に任せる。建物は見える範囲に応じて窓枠・軒先・外壁目地を優先し、内装は外から見える箇所や依頼された部屋から作る。

6. **テクスチャや投影は面の向きに合わせて張り分ける**。正面・側面・上面で見え方が違う場合は、それぞれの面に合った画像と投影を用意して自然につなぎ、正面写真を曲面の裏側まで引き伸ばさない。写真に写り込んだ影、背景色の混入、造形した目や窓とテクスチャ側の二重写りもチェックする。

7. **既存のボーンやアニメーションは使える限りそのまま活かす**。形状を作り直す場合は変化に合わせてウェイトと可動部を調整し、元のアニメーション名で問題なく再生できることを確認する。

8. **仕上がりは Studio に取り込んで描画した結果で判定する**。Blender や制作途中の画面だけで完了にしない。set_scene_view_camera が返したカメラ位置と注視点を控えておき、修正後も同じ値で撮影して照明・角度・画面上の大きさを揃えたうえで前の版と比較する（元の版や前回版があれば三者比較する）。比較用の一時的な配置・倍率変更はモデル自体の修正と区別し、全体斜め視点と修正部位の拡大（必要に応じて屋根・窓・壁の取り合いなど）を撮る。改善点や残課題が画像から判別できなければ撮り直し、動くモデルは Play が使える環境で同じアニメーションの同じタイミングでの変形姿勢を比べる。

9. **症状ごとに具体的な合格ラインを確認する**。口や窓は斜めから見ても奥行きがあり黒い板に見えないこと。ヒレや庇は本体から自然な断面でつながり、付け根に不自然な段差がないこと。膜や布は動いても付け根が浮かないこと。写真の目と造形した目が二重に重なっていたら、テクスチャ側の目を消してから再確認する。

10. **既存の配置を維持したまま差し替えられる状態で引き渡す**。編集元のある Model は reimport_model_asset で更新して Model ID と配置を維持し、別 Model へ差し替える場合は set_entity_model を使って Entity の名前・Transform・他 Components を残す。差し替え後は名前・大きさ・向き・Material と Texture・必要なアニメーションを確認する。編集元の .blend やソースを残し、直した箇所・残る課題・使用した資料・未確認の環境を報告する（確認範囲がモデル単体・Scene 内・実機のどれかも明記する）。複数モデルを扱った場合は対象と採用版を一覧にし、対象外の Model を誤って追加・置換していないか照合する。

## 必要なときに読むガイド

`get_world_authoring_guide` の topic は、実際に使うものだけを取得する。作業前にすべて読み込む必要はない。

- `r3f`（制作方法）: 再利用できる静的な TSX 部品を編集可能な Scene の Entity として組み立て、後から修正できるよう完全なソースを保存する。
- `assets`（制作方法）: 空間の一部として必要な形状・質感・機能を備えた、既存素材や外部素材を選んで配置する。
- `blender`（制作方法）: 静的ソースの取り込みでは表現しきれない、独自の曲面や立体構造を Blender で制作する。
- `spatial-ui`（設計）: VR や WebGL で読みやすい案内空間を設計する。情報の優先順位、余白、人に見やすいカード寸法、文字設定、再利用できる静的ソースの例をまとめている。
- `environment`（設計）: 既存の制作物を壊さずに Skybox・IBL・照明を整える。VR や WebGL での描画負荷の目安と対象端末での確認方法もまとめている。

## Studio での制作と確認

静的ソースで制作する場合は、`apply_r3f_scene` でソースを持つルート Entity を作成・更新する。修正前に `get_entity_components` でそのルートを読み込み、完全な `r3fAuthoring.source` を使って編集する。通常の Component コード取り込みでは保存済みのソースを更新できない。対応する操作や制限は、ツールのスキーマと返却された機能情報で確認する。

ワールド全体の制作では、`get_world_authoring` で作業を再開するか、`begin_world_authoring` で設計内容と完成条件を保存する。書き込みには現在の revision を使う。保存した結果をスポーン視点（spawn）と斜め上からの俯瞰（iso）で撮影し、`review_world_authoring` で完成条件を一つずつ確認・記録したうえで、`complete_world_authoring` で完了する。小規模な直接編集では、ワールド全体の制作手順を開始する必要はない。

Studio ChatGPT・MCP・このスキルの基本方針は、[共通ガイド](../../../src/lib/visual-editor/world-authoring-guide.json)で一元管理している。
