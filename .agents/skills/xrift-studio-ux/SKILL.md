# XRift Studio UX

## Overview

制作の目的、画面の状態、主操作、完了後の到達点を一つの流れとして揃える。

操作導線を変更するときは、リポジトリの [UX 原則](../../../docs/UX_PRINCIPLES.md)、[マイクロインタラクション Wiki](../../../docs/UX_INTERACTIONS.md)、`AGENT.md` の該当箇所を読む。文言だけの修正で全資料を読み直さない。実装中は既存の `UpdateDialog.tsx`、`ProjectLibrary.tsx`、`ProjectCard.tsx`、`EditorView.tsx` を再利用できる実例として参照する。

## 設計手順

1. ユーザーが得たい結果を一文で定義する。内部 API や画面名を目的にしない。
2. 操作前、処理中、成功、失敗、復帰先の状態を列挙する。
3. 各状態に、現在の事実、主操作、次に開ける対象を置く。
4. 成功時は通知だけで完結させず、作成物、URL、更新済み状態のいずれかに到達できるようにする。
5. 一覧へ戻る機能なら、結果を識別でき、新規作成の入口も失われないことを確認する。
6. 対応する `MI-xx` を Wiki から選び、動き、無効化、文言、復帰先を機能仕様に記録する。新しい動きは Wiki に追加する。
7. 実画面の確認は xrift-studio-verify スキルの手順（変更対象に応じた静的チェック・ブラウザ・Tauri MCP）で行う。

## 実装上の判断

- 必要な更新は起動後に検知し、現在と最新の差分、実行、延期を同じ導線に置く。
- 作成・起動・公開の成功後は、作成物を開くか、URL をすぐ開ける状態を残す。
- ワールドの公開前は、タイトル、説明、サムネイルがテンプレートのままなら編集へ案内し、保存後に残りの項目を再確認してからアップロードする。
- 一覧では、新規作成を先頭に置き、サムネイルと最小限の説明で各項目を見分けられるようにする。
- 実行中はラベルと無効化で二重操作を防ぐ。安全でない中断は可能であるように見せない。
- 白とニュートラルカラーを基調にし、ブランド色、影、動きは主操作と意味のある状態のためだけに使う。
- 主要操作には読み上げ可能なラベルまたは `title` を付ける。Markdown、画面文言、コミットメッセージでは絵文字を使わない。

## コンポーネント名の表記

コンポーネント名はすべて英語で表示する。Add Componentで選んだ名前をInspectorの見出し、削除・有効化の操作、通知、Hierarchy、カタログでも使う。Mesh Renderer、Rigid Body、Box Collider、Mesh Collider、Transformなどを「メッシュの描画」「物理挙動」「衝突判定」「位置・回転・大きさ」へ翻訳しない。公式XRift Componentも英語の正式名を使う。

表示名はAdd Componentのレジストリを参照し、画面ごとに別の翻訳表を作らない。Lightの種類やAudio Sourceの種類も選択内容と照合する。効果・操作・単位の説明は短い日本語で添えてよいが、英語名を日本語の説明へ置き換えない。保存済みIDやAPI名は変更しない。

文言を変更したら、追加メニュー → 追加後の見出し → 操作と通知の順で同じ英語名になっているか確認する。

## Entity作成とComponent追加

Entityの作成メニューは選択状態によって既存Entityへの追加へ切り替えない。新しいEntityを作る操作と、Inspectorや対象Entityの右クリックからComponentを追加する操作を明示する。候補、名前、順序、重複・依存条件は共通定義から用途に合わせて選ぶ。Transformのような必須Component、同じ機能の旧追加口、既存のメッシュや子要素が必要で単独では成立しない項目をEntity作成候補に並べない。追加できない理由は選択前に示す。

すべてのEntity配置候補を折りたたみにまとめる。先頭のEntityに空のEntityを置き、PrimitiveにCube、Planeなど、WorldにSpawnPointを入れる。Entity追加の検索欄は置かず、Entity、Primitive、World、Light、UI、Audio、Effect、XRiftの折りたたみで選ぶ。形状名を「床」のような用途名にしない。Light、Text、SpawnPointなど配置するものを選びやすくし、Rigid Bodyなど既存Entityへ付ける機能を新規Entityの候補へ混ぜない。XRiftの配置は同じ機能のPrefabとComponentを二重に並べず、一つの候補にまとめる。「Component付きEntity」のような内部構成を分類名に使わない。

複数選択時の右クリックでは名前変更・削除などの操作を上に出し、EntityやComponentの追加候補を混ぜない。単体選択と複数選択で操作の対象が変わる場合は、選択状態を保って対象に合うメニューを表示する。

## 完了前の確認

AssetsはAssets直下にフォルダー階層を表示し、その下に種類の絞り込みを置く。Modelsなどの種類は左側の絞り込みとして扱い、素材一覧にフォルダー風の項目として並べない。素材一覧のフォルダーは実際のフォルダーだけにし、種類を選んだときは該当する素材だけを表示する。空のワールドにはシーンが実際に使う素材だけを入れ、テスト用Material、サンプルPrefab、空のStarter Libraryフォルダーを初期生成しない。PrimitiveのMaterialは配置時に必要なものだけ追加する。

- 状態、主操作、成功後の到達点、失敗時の復帰手段をすべて確認する。
- 作成または更新後に一覧と選択状態が最新になっていることを確認する。
- 主要導線をスクリーンショットまたは DOM で確認し、操作名に頼らず次の一手を理解できるかを確認する。
- `pnpm typecheck` と検証目的の実機起動・MCP 読み取りは許可なしで行ってよい。`pnpm tauri:build` と書き込みを伴う実機 UI 操作はユーザーの許可後に実行する。

Assetsのカードは高さと補助情報を抑え、素材名とプレビューを見渡せる密度にする。プレビュー未生成・読込中・読込失敗時は種類のアイコンを中央に表示し、「プレビュー準備中」などの代替テキストを繰り返し並べない。素材自体の欠損や解析失敗の警告は区別して残す。

Assetsのリストは素材名を中心に詰めて表示し、documentやファイルパス、通常時のreadyを各行に並べない。素材一覧のカードや行に配置ボタンを置かず、右クリックの「シーンへ配置」を使う。配置可能かどうかでカードの高さや名前の幅が変わらないようにする。

Assetsのリストには、取得できるファイルサイズをKB・MBなどの単位で名前の右に表示する。サイズは一覧で比較する情報として残し、読める文字サイズと右揃えで揃える。

使い方ガイドはdocs/guideの原稿を公開版とアプリ内で共有する。ヘルプは作業場所に対応するページを開き、閉じたら元の操作へフォーカスを戻す。旧Wiki原稿や旧URL用の移行ページは残さない。画面の操作名を変えたらガイドの手順も同じ作業で合わせる。
