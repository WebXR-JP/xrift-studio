# XRift ワールドの制作工程

依頼と現在の Scene から制作・調整し、画像と動作で完成条件を確認する。依頼外の要素を追加しない。

## 作業範囲と進め方

実行の判断は `AGENT.md` に従う。依頼済みの制作・検証は途中で許可を取り直さず進める。認証、対象作品の取り違え、接続不能など解決できない条件は具体的に報告し、進められる工程を終える。公開を依頼されていなければ保存・検証までで完了する。

`get_editor_context`、`list_entities`、利用可能な tool で現在の Scene と機能を確認する。既存作品を開く場合は依頼との対応を確かめ、対象が不明なまま別の作品を変更しない。

## 設計図

新規制作や大きな変更では `references/blueprint-template.md` を使い、現状を確認してから書き込み前に設計図を作る。配置・色・雰囲気だけの小さな調整では、変更対象と完成条件の短い記録でよい。制作セッションを使う場合は既存の begin/update/finish tool の契約を守る。

依頼されていない体験や設備を必須にしない。ツールの数や過去の作例ではなく、依頼と必要な品質から手段を選ぶ。前提を変えた場合は理由を記録する。

### 体験と設備

体験設計を依頼された場合は、訪問者が何をするかを決める。景観や配置だけの依頼には体験を追加しない。交流・共同作業・発表のワールドでは、画面共有を最初に検討し、採用するか省くかと理由を設計図に書く。ミラーはアバター確認や交流、TagBoard はイベントで参加者がタグを選ぶ用途に合わせる。すべてのワールドに一律で付けない。

`list_component_definitions` または `get_world_authoring` の `worldComponents` に、用途、配置の手順、公式のプロパティ定義、既存設備が返る。既存設備を調べてから追加・調整する。現行のタグ選択部品は `TagBoard` であり、別の `TagMarker` API があると推測しない。詳しい判断は `references/world-components.md` にある。

## 工程

以下は新規制作の目安。既存 Scene の状態と依頼に合わせて工程を選び、順序を調整する。小さな変更では対象と影響箇所を検証し、全体の再制作をしない。

### 1. 土台

`get_editor_context` と `list_entities` で、スターターの床・太陽・スポーン位置を確認する。設計図の床と違うものが置かれていたら、削除するか差し替える。そのうえで、床と大きな構造物を設計図に合わせて作る。プリミティブの初期の灰色 Material のまま残さない。置いた物は `get_entity_bounds` / `sample_terrain_point` で地面への接地を確かめる。

### 2. 主役

設計図で定めた主な体験に必要な設備と、景観の主役を、飾り付けより先に作る。画面共有のワールドならスクリーンと観客・操作する人の居場所、イベントなら受付と待機する場所もこの段階で確保する。素材の入手先の一覧は `references/asset-sourcing.md` にある。入手先に優劣はないので、設計図の品質の水準に合うものを選ぶ。画面共有・ミラー・タグ選択には公式 Component を使い、その見た目を自作の板や Script で代用しない。その他の動くもの・繰り返し現れるもの・反応するものは Script で作る（`references/scripting-patterns.md`）。

### 3. 光と空

空、環境光、フォグは `update_scene_settings` でまとめて設定する。ばらばらに変えると、空だけ夕方なのに光が昼のままといったちぐはぐな状態になる。

ポストエフェクトを使うかどうかは、設計図の「品質の水準」に合わせて決める。使う場合は、有効にする前後で `capture_scene_view` を撮って見比べる。見た目に差がなければ無効にする。

### 4. 設計図の残り

設計図に書いた残りの要素（小物、音、仕掛け、動き）を作る。

### 5. 検証

1. `set_scene_view_camera` でカメラをスポーン位置・目の高さに置き、主役のほうへ向けて `capture_scene_view` を撮る。
2. `set_scene_view_camera { preset: "iso" }` で俯瞰に切り替え、`capture_scene_view` を撮る。
3. `capture_scene_debug { action: "metrics" }` の値を、設計図の「予算」と照合する。
4. 2 枚の画像を設計図の「完成の条件」と見比べて、合否を判定する。判定の根拠は完了報告に書く。
5. 設備がある場合は、観客席の前列・後列・端、操作位置、受付など必要な利用視点からも撮影する。表示面の向き、読みやすさ、遮蔽物、通路、壁や枠との収まりを確認する。追加画像には `authoringView` を付けず、スポーン・俯瞰の証拠を上書きしない。
6. 配置と機能の確認を分ける。画面共有の開始・表示・停止、タグ選択、ミラーでのアバター確認は対応する実行環境で確認し、参加者間の共有・同期は複数クライアントで確かめる。Edit の待機画面だけで動作確認済みにしない。確認できない項目は未検証として報告し、その条件を合格にしない。

見た目は画像、負荷はmetrics、機能は実行結果で確認し、互いを代用しない。

## 完了報告と復旧

設計図または変更記録、画像の保存先、metricsと予算、完成条件の判定、前提、未検証・未完了と理由をまとめる。

- `harness` が同種の書き込み反復を警告したら画像を撮り、確認できた欠点を修正する。欠点がなければ次へ進む。
- 外部モデルは `search_external_assets` の `polycount` と予算を比較してから取り込む。
- Scriptの失敗は `get_editor_context.scriptRuntime` の変換・実行エラーを直してPlayで再確認する。
