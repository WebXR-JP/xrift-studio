# 設計図の書式

設計図は、最初の書き込み前に作成してください。get系のツールで現状を確認してから書けます。

- 最初の報告と完了報告には、同じ設計図を載せる。
- 数値の上限、予算、完成条件は、依頼内容とワールドの規模、公開先に合わせて決めてください。判断できない欄は空欄にし、「前提」に理由を書きます。
- 項目は依頼内容に合わせて増減できます。
- テーマの指定がなければ、依頼された用途、人数、雰囲気に合うものを1つ選んでください。
- 案は原則1つに絞ります。複数案の比較を依頼された場合は、各案と推奨する案を示してください。

```text
設計図
- 品質の水準: <軽さ優先 | 標準 | 高品質。依頼文のことばから選ぶ>
- 場所と用途: <誰が来て、何をする、どんな場所か>
- 雰囲気: <時間帯、天気、色の印象>
- 床: <床の種類と大きさ。Terrain を使う場合は、起伏をどのように使うか>
- 主な体験: <画面を見せて話す、アバターを見せ合う、発表を聞くなど>
- 設備: <画面共有の採用/省略と理由。ミラー、タグ選択、動画などは用途に合わせて選ぶ>
- 利用場所と動線: <観客・操作する人・受付と待機列の場所、入口からの通路、設備の向き>
- 景観の主役: <体験の場所を印象づけるもの>
- 動きと反応: <何が動き、何に応えるか。なければ「無し」>
- 入れないもの: <依頼文に合わないもの>
- 予算: <三角形、draw call、容量の上限。各要素にかけられる手間の上限>
- 完成の条件: <景観、設備の見え方・操作・移動、必要な共有や同期の動作を確認できる条件>
- 前提: <確認せずに決めたことと、その理由>
```

## 完了報告

完了報告は [制作スキル](../SKILL.md#完了報告と復旧)、画像と動作の確認は同スキルの「検証」に従う。

設備を採用したら、`begin_world_authoring.criteria`に利用位置からの配置確認と動作確認を記載してください。たとえば画面共有なら「客席の前列・後列・端から表示が見え、操作位置と通路が塞がれていない」「対応する実行環境で共有開始・表示・停止を確認した」のように分ける。追加画像は`authoringView`なしで撮り、画像の保存パスと実行環境で確かめた内容を判定根拠に残す。未検証の機能を合格扱いにしない。
